# Changelog — Tycoon v116

## 2026-09-28 (семнадцатый заход) — Грузовик мог ждать «на повороте» другого грузовика неограниченно долго: статичный tie-break в `serviceVehicleYieldFactor()` не учитывал реальное время ожидания

### Жалоба пользователя (дословно, русский)

> «я бы проработал бы еще над физикой машин, а то одна ездит, а другая стоит на повороте, ждет
> пока проедет другая»

### Где искать живую логику (только последнее присвоение в файле — действующее)

`grep` по `yield`/`giveWay`/`junction` нашёл несколько слоёв, но реально управляющая функция —
одна: **`serviceVehicleYieldFactor(vehicle, target)`, `tycoon-v116.html:7269-7345`** (не
переопределяется позже — единственное определение во всём файле). Она вызывается из
`moveWorkVehicle()` (`:7415`, оборачивается v65/v82, но обёртки не трогают саму функцию) на
каждом кадре для каждого грузовика доставки, отдельно от:
- `depotTokenV65` (`:29960`, v65-блок) — мьютекс «один грузовик на узкой дороге склада за раз».
  Проверено живо (`traffic116/repro2.mjs`): у него ЕСТЬ рабочий self-release
  (`tokenOwnerValidV65()` проверяет каждый кадр, что владелец токена ещё реально едет/грузится),
  и второй грузовик, которому токен не дали, просто уходит в `idle` и повторяет попытку через
  `.55–1.4с` — это не тот баг, который жалуется пользователь (не «одна ездит, другая ждёт», а
  короткий, самовосстанавливающийся ретрай). Живое поле `_v65DepotWait` (`:29992`) при этом нигде
  не читается (write-only) — отдельная, более мелкая недоделка, не влияющая на симптом сейчас,
  оставлена как есть (не тот скоуп).
- `deadlockGuardV74()` (`:30794`, v74-блок, сам себя называет «the final deadlock controller») —
  таймаут-брейкер, но ТОЛЬКО для взаимного клинча: пара грузовиков, у которых у ОБОИХ
  `currentSpeed<=.075` одновременно ≥3.5с (`:30801,30804`). Строка `:30801`
  (`if((ua.currentSpeed||0)>.075||(ub.currentSpeed||0)>.075)continue;`) явно и намеренно
  ИСКЛЮЧАЕТ именно случай из жалобы — «одна ездит [скорость>0], другая стоит» — из этой защиты.
- `cityVehicleAvoidanceV82()` (`:31562`, амбиентные городские машины/автобусы) — у неё, для
  сравнения, tie-break уже комбинирует `priorityV82()` (класс/приоритет) и `stableIdV82()`
  (`:31598-31599`) как только детерминированный АРБИТР, а не единственное правило — она не
  затронута этим багом.

### Корень (подтверждён живыми замерами, не чтением кода)

`serviceVehicleYieldFactor()` разруливает НАСТОЯЩИЙ конфликт-пересечение (разные курсы, не
попутное движение — попутное «физически позади» уже честно хард-стопится раньше, `:7298-7307`,
не трогалось) чисто СТАТИЧЕСКИМ tie-break'ом (`:7315-7323`): сначала кто едет с грузом
(`mineLoaded`/`otherLoaded`), при равенстве — простое сравнение строк `logisticsId`. Ни то, ни
другое не зависит от того, кто дольше стоит/раньше подъехал к перекрёстку.

Живое подтверждение через ПРЯМОЙ вызов настоящей, неизменённой функции
(`traffic116/repro3.mjs`, синтетические, но геометрически реалистичные объекты-грузовики):

| сценарий | результат ДО фикса |
|---|---|
| L и W на перекрёстке (курсы 90°/45°/135° друг к другу), у обоих `_auditStuck=0` (только подъехали) | `factor=0` — корректно, это ожидаемая безопасная реакция на первую встречу |
| L проигрывает статичный tie-break (лексикографически больше по `logisticsId`), стоит **6 РЕАЛЬНЫХ секунд** (`_auditStuck=6.0`), W вообще никогда не стоял (`_auditStuck=0`) | **`factor=0` — то же самое, ноль изменений от времени ожидания** |

Второй ряд — прямое доказательство: сколько ни жди, статичное правило не даёт приоритета.
Живой полноинтеграционный прогон (`traffic116/repro4_live.mjs`, два настоящих грузовика доставки
из реального `serviceVehicles`, тикается настоящим `moveWorkVehicle` через настоящий
`requestAnimationFrame`, а не мок) на перекрёстке X-типа: грузовик-«проигравший» (искусственно
проставленный `logisticsId`, чтобы стабильно проигрывать сравнение строк) простоял **20 из 20
реальных секунд** измерения без единого сантиметра прогресса (`z: 0.024 → 0.066`, `speed=0` на
протяжении всего окна), пока грузовик-«победитель» продолжал существовать/«ездить» у того же
перекрёстка.

### Фикс (`tycoon-v116.html:7314-7339`, внутри уже существующей функции, без нового патч-слоя)

Внутри именно этой crossing-ветки добавлена проверка реального времени ожидания ПЕРЕД статичным
правилом, с уже существующим полем `_auditStuck` (его считает `updateVehicleProgressWatch()`,
`:7230-7251`, для КАЖДОГО грузовика на каждом кадре — новой бухгалтерии не требовалось):

```js
const myStuck = ud._auditStuck || 0, otherStuck = other.userData?._auditStuck || 0;
if (myStuck > 2.0 && myStuck > otherStuck + 1.2) {
  yieldToOther = false;
} else {
  /* прежнее статичное правило без изменений */
}
```

Выбор именно такого фикса, а не альтернатив из списка задания:
- **Не просто таймаут-заглушка** — порог `2.0` привязан к тому же `_auditStuck`, что уже
  используется в файле как «застрял» (соседняя ре-роут-логика на `:7429` берёт `>2.6` для того же
  поля), то есть это не новая магическая константа, а согласованное с существующим кодом продолжение
  уже принятого в файле понятия «застрял». Margin `1.2` — намеренно шире, чтобы близкое по времени
  ожидание с обеих сторон (взаимный, почти синхронный клинч) НЕ начинало щёлкать приоритетом каждый
  кадр от дрожания таймеров — эта симметричная ситуация остаётся зоной `deadlockGuardV74()`,
  который уже физически расталкивает такие пары (`advanceWinnerV74()`, `:30773`).
- **Не трогает `sameLane`-ветку** (`:7296-7307`, реальное «физически позади») — фикс применяется
  СТРОГО после неё, так что грузовик физически не может «проехать сквозь» реальный кузов другого
  грузовика впереди в своей же полосе; только меняется исход именно crossing-приоритета.
- **Не новый патч-слой** — правка целиком внутри тела существующей `serviceVehicleYieldFactor()`.

## 2026-09-28 (шестнадцатый заход) — Фикс гонки boot-порядка: `tuneMechanicsV43()` откатывал `constructionDuration` v80 назад к короткой v43-формуле

Прямое продолжение честной находки пятнадцатого захода (`e9e5248`, см. секцию ниже,
«Найдено, но НЕ исправлено»): та секция подробно описала механизм, но сознательно не чинила
его как более широкую, отдельную от узкого скоупа правку. Этот заход — именно эта правка,
проверенная живым прогоном перед изменением кода (не поверила чужому отчёту вслепую), и
закрытая в корне без нового патч-слоя.

### Механизм (подтверждён живым замером, не только чтением кода)

Три релевантных определения `constructionDuration` в файле:

- **v1 / база** (`tycoon-v116.html:1665-1669`): `base=3.25+stageIdx*0.23+(level-1)*0.42`,
  `speedMult=pow(0.84,fieldUpgrades.construction||0)/constructionSpeedMultiplier()`,
  `clamp(2.0,6.4)`. Определяется синхронно при парсинге документа, самое первое присвоение.
- **v43-«тюнинг»** (было на `tycoon-v116.html:19198-19204`, внутри `tuneMechanicsV43()`):
  безусловно ПЕРЕЗАПИСЫВАЛА `constructionDuration` на свою собственную, независимую формулу
  (`base=2.75+stageIdx*0.18+(level-1)*0.34`, `clamp(1.7,5.35)`) — не оборачивая и не вызывая
  предыдущее значение (`_constructionDurationV42` захватывался, но НИГДЕ не использовался —
  мёртвая переменная, явный след того, что композиция была задумана, но не реализована).
  `tuneMechanicsV43()` вызывается только из `runV43Polish()`
  (`tycoon-v116.html:19221-19236`), которая навешена на
  `DOMContentLoaded`+`setTimeout(...,80)` (`tycoon-v116.html:19235-19236`) — то есть выполняется
  ОТЛОЖЕННО, позже любого синхронного `<script>`-блока документа, независимо от того, где по
  тексту файла эти блоки физически расположены.
- **v80-crew-construction-loop** (`tycoon-v116.html:31205-31209`, внутри
  `constructionPriorityMultiplier`'а соседнего IIFE): оборачивает ТЕКУЩЕЕ на момент своего
  исполнения `constructionDuration` (`constructionDurationBeforeV80`) и умножает результат на
  `1.62`, зажимая в `[5.1,10.4]` — специально придуманная более позднreadable механика «бригаде
  нужно физически успеть дойти до площадки» (комментарий `tycoon-v116.html:31194-31203`). Этот
  блок расположен физически НИЖЕ v43-блока по тексту файла, но выполняется СИНХРОННО при парсинге
  — то есть раньше отложенного `runV43Polish()`.

Итог по порядку РЕАЛЬНОГО исполнения (не порядку текста в файле): v1 определяется → v80
синхронно оборачивает v1 (`constructionDuration` = `clamp(v1(...)×1.62, 5.1, 10.4)`) → **только
затем**, спустя ≥80мс после `DOMContentLoaded`, `tuneMechanicsV43()` безусловно перезатирает
`constructionDuration` целиком на свою короткую формулу, полностью выбрасывая обёртку v80. Из-за
этого длинная v80-версия существует только в узком окне между парсингом и первым срабатыванием
таймера — и не переживает ни одной реальной игровой сессии.

**Живое подтверждение до фикса** (`constructiontiming116/diag_construction_duration.mjs`,
свежий/пустой сейв, `constructionDuration(0,1,false)` замерено сразу после `load` и далее на
+50/+100/+300/+1300мс):

| момент замера | значение до фикса |
|---|---|
| сразу после `page.goto(..., {waitUntil:'load'})` | `2.75` |
| +50мс / +100мс / +300мс / +1300мс | `2.75` (не меняется) |

Значение `2.75` — это именно v43-формула (`2.75+0*0.18+(1-1)*0.34=2.75`, `speedMult=1` на чистом
сейве). Оно одинаково НА ВСЕХ точках замера, включая «сразу после load», потому что за время
полной загрузки страницы (сеть+ресурсы) отложенный `setTimeout(...,80)` уже успевает сработать —
то есть с точки зрения любого живого кода игры v80 фактически никогда не был активен ни секунды
в браузере. Это соответствует находке пятнадцатого захода (`constructionDuration(0,1,false)`
возвращает `2.75`, не `~5.1`), но с уточнением точного механизма: значение стабильно `2.75` во
ВСЕЙ временной шкале, а не просто «в какой-то момент откатывается».

### Фикс (`tycoon-v116.html:19196-19222`, внутри уже существующей функции, без нового патч-слоя)

`tuneMechanicsV43()` больше не трогает `constructionDuration` вообще — удалены строки
безусловного переприсваивания (`_constructionDurationV42`/`constructionDuration=function(...)`),
оставлена только остальная часть функции (`districtTrafficSpeedFactor`, вызов `updateHUD()`).
Обоснование выбора именно этого варианта (а не «сложить обе формулы» или «звать v43-формулу
из v80»): v80 — более позднеавторская, явно документированная («base build durations are long
enough for a crew to physically arrive», `tycoon-v116.html:31198-31199`) владелица этой константы;
её собственное присвоение уже само оборачивает то, что было текущим `constructionDuration` на
момент её синхронного исполнения (то есть v1), поэтому просто убрать конкурирующее позднее
перезатирание — минимальное, точное по цели изменение. `tuneMechanicsV43()` как функция не
удалена (по инструкции задания) — её остальной тюнинг (`districtTrafficSpeedFactor`,
`updateHUD()`) продолжает работать как раньше.

### Совместимость с фиксом первого дома (`e9e5248`, тот же файл, `constructionPriorityMultiplier`, `tycoon-v116.html:31262`)

Ранний `return base` при `npcWorkers.length===0` (полностью пропускает штраф за отсутствующую
бригаду) не изменён и не затронут — этот фикс трогает только `constructionDuration` (саму
длительность стройки), а не `constructionPriorityMultiplier` (скорость прохождения этой
длительности). Композиция: `base` в `constructionPriorityMultiplier` больше не зависит от
`constructionDuration`, так что оба фикса ортогональны по коду. Но численно результат
меняется: раз `build.duration` теперь длиннее (`5.265` вместо `2.75`), а множитель скорости для
дома 0 остаётся `1` (полная скорость, фикс `e9e5248` не тронут), реальное время постройки дома 0
пропорционально вырастает.

**Живой замер** (`constructiontiming116/diag_house0_timing.mjs`, чистый сейв, дом 0, 0 рабочих,
от `purchaseCurrentPad()` до `underConstruction===false`): **33.4с** реального времени в этой
песочнице (одиночный прогон; тот же тип замера, что дал `e9e5248` диапазон `12.3-20.4с`).
Рост примерно в 1.6-2.8 раза (`33.4 / [12.3..20.4]`) — что ожидаемо и согласуется с ростом самой
`constructionDuration` в `5.265/2.75≈1.914` раза: это НЕ регрессия от текущего фикса, а прямое,
неизбежное следствие того, что v80-надбавка наконец реально применяется (раньше не применялась
вообще). Абсолютное число (`33.4с`) остаётся хорошо в рамках требования `VISION.md` «не длиннее
минуты-двух» для первой постройки, и, как уже отмечал `e9e5248`, эта песочница сама по себе
раздувает реальное время из-за `Math.min(clock.getDelta(),.075)` (`tycoon-v116.html:13901`) и
низкого fps под нагрузкой headless/swiftshader без GPU — на реальном 60кадр/с устройстве это
означает рост с ~2.75с до ~5.3с «сырой» длительности, что тривиально укладывается в тот же бар.
Фикс `e9e5248` НЕ требует изменения своего порога/логики — он адресует именно факт полной
заморозки прогресса (0-скорость), а не абсолютную длительность, и продолжает работать корректно
поверх новой, более длинной `constructionDuration`.

### Проверка «дальнего рабочего» (дом 1 после завода) — НЕ стало хуже (не чинилось, по скоупу)

Живой замер (`constructiontiming116/diag_house1_timing.mjs`): чистый сейв → мгновенно
достроен дом 0 (служебный хак теста, не имитирует реальный игровой путь) → живой вызов
`buildIndustrialZoneV116()` (спавнит ровно 4 реальных рабочих `builder/rigger/foreman/loader`,
как в проде) → `purchaseCurrentPad()` для дома 1 → опрос `constructionPriorityMultiplier`,
`build.timer`, `build.duration` каждые 2с реального времени поллинга до ~124с.

Наблюдение: `build.duration=5.6376` (подтверждает формулу выше). Таймер прогресса ведёт себя
ровно так, как описывает существующий, НЕ относящийся к этому фиксу код
`constructionPriorityMultiplier` (`tycoon-v116.html:31263-31279`, комментарий `31275-31277`):
~4.2с полной заморозки (`_v80CrewWaitSeconds<4.2`), затем ползёт на `×0.18` до тех пор, пока
бригада физически не подойдёт (`onSiteCrewV80`, дистанция `≤0.52`). В моём замере таймер дополз
до `2.931165` (≈52% от `5.6376`) и там ЗАСТЫЛ на десятки секунд подряд — но это оказалась НЕ
крю-механика, а отдельный, не относящийся к этому фиксу «gate» ожидания физической доставки
материалов (`addConstructionProgress`/`nextPendingDelivery`, `tycoon-v116.html:5668-5678`,
`updateConstructionSites`, `tycoon-v116.html:13932-13951`) — `gate*build.duration=0.52×5.6376=
2.93155`, совпадает с точностью до округления. Это артефакт МОЕЙ методики теста (я выставил
`concrete=999`/`metal=999` напрямую через `evaluate()`, не через реальный путь покупки/доставки
грузовиком — поэтому тикет доставки (`ticket.delivered`) никогда не выставляется, и стройка
корректно, но вечно «ждёт грузовик», которого мой тест не запросил). Это не ошибка фикса и не
новая находка — просто граница моего конкретного диагностического скрипта, честно
задокументированная, а не выданная за «дом 1 всё ещё не строится».

Важный для скоупа вывод по композиции: crew-wait-механика (`_v80CrewWaitSeconds`, `4.2с`,
`×0.18`) измеряет ожидание в РЕАЛЬНЫХ секундах (`build._v85PriorityDt`, реальный `dt` кадра) —
она НЕ зависит от `build.duration` и потому НЕ меняется этим фиксом ни на секунду: сколько
реального времени рабочему нужно дойти до площадки — определяется исключительно скоростью
рабочего и дистанцией (`~1.0-1.45` юнита/сек, `~48-58` юнитов, как и в находке `e9e5248`), что
этот фикс не трогает вообще. Меняется только ОБЩАЯ длительность стройки (знаменатель) — то есть
после того как бригада всё же дойдёт (или ожидание истечёт по watchdog'у `wait<4.2?0:.18`),
оставшийся путь по таймеру теперь длиннее в те же `≈1.62×`, что и для дома 0. Итог: «мёртвый
отрезок» (время до появления/дохода бригады) НЕ стал длиннее — он определяется физикой ходьбы,
не тронутой этим фиксом; ОБЩЕЕ время стройки дома 1 стало длиннее пропорционально росту
`constructionDuration` — то есть именно то поведение, которое v80 и было задумано дать (более
длинная база, чтобы бригаде было физически когда дойти), теперь наконец реально работает для
дома 1, а не только формально существует в файле. Дальнейшая перебалансировка «домашней базы
рабочих ближе к жилой спирали» остаётся отдельной, более рискованной задачей вне скоупа этого
захода — по прямому указанию не трогать её здесь.

### Найдено и исправлено: 2 реальных бага

#### 1. Первый дом строился ~59 секунд вместо ~12-20 — «ждать бригаду, которой физически не существует»

Живой замер (`scratchpad/firsthour116/diag_construction.mjs`) на чистом сейве: купил дом 0
(`purchaseCurrentPad()`), затем просто ждал, ничего не трогая. Дом достроился только на
**+59.4с** реального времени — далеко за «минуту-две» с запасом на первую же постройку в игре,
и прямо нарушает `VISION.md` («Первые доски, первый грузовик. Игрок понимает связку "кружок →
стройка → доход"» — подразумевает быструю, не тянущуюся отдачу).

**Корень** (`tycoon-v116.html:31219`, `constructionPriorityMultiplier` внутри
`<script id="v80-crew-construction-loop">`): если у стройки нет физически стоящей рядом
бригады (`onSiteCrewV80(build).length===0`), функция сначала полностью замораживает прогресс
(`base*0`) на первые 4.2 РЕАЛЬНЫЕ секунды ожидания, затем даёт лишь 18% скорости
(`base*0.18`) — специально придуманная механика седьмого-по-счёту (не этого сеанса) патча
«бригада должна физически дойти до площадки». Но на честно пустом старте (`f9ade3a`,
`VISION.md` «Старт новой игры: пустой мир») до постройки завода в игре **нет вообще ни одного**
`npcWorkers` — `spawnIndustrialCampLifeV116()` (единственный источник первых 4 рабочих) вызывается
только из `buildIndustrialZoneV116()`. Ждать бригаду, которая физически не может существовать —
не полезное ожидание, а голая заглушка тайминга. Живой замер подтвердил: `build.duration` дома 0
на практике равен `2.75` (v43-формула; см. отдельную находку ниже про то, почему в файле
формально «уже есть» v80-надбавка `*1.62`→5.1-10.4, а по факту работает старая v43), при этом
прогресс почти не двигался первые ~15 реальных секунд (см. `crewWaitSeconds` в логе), а затем
полз по 0.18×.

**Фикс** (`tycoon-v116.html:31219-31232`, внутри уже существующей функции, без нового
патч-слоя): добавлена одна ранняя проверка —
```js
if(typeof npcWorkers!=='undefined' && npcWorkers.length===0) return base;
```
— если бригады не существует НИГДЕ в игре (не «эта конкретная стройка её не нашла», а «во всей
игре пока нет ни одного рабочего»), штраф не применяется вообще (полная скорость, как при
«бригада на месте»). Это условие затрагивает ТОЛЬКО узкое окно между пустым стартом и
постройкой завода — `buildIndustrialZoneV116()` сразу создаёт 4 рабочих
(`spawnIndustrialCampLifeV116(4)`), и с этого момента бонус больше не применяется никогда
(дом 1 и далее — прежняя механика ожидания бригады без изменений). У старых сейвов
`industrialZoneBuiltV116` по умолчанию `true`, значит `spawnAmbientLife()` создаёт рабочих
безусловно при загрузке — `npcWorkers.length` для них никогда не бывает `0`, фикс их не
касается совсем.

**Живой результат до/после** (`scratchpad/firsthour116/diag_construction.mjs`,
`diag_after_fix.log`, плюс реальный игровой путь в `run2.log`/`run3.log`):

| | до фикса | после фикса |
|---|---|---|
| Дом 0 строится (реальное время, чистый сейв, 0 рабочих, чистое измерение от покупки до готовности) | **~59.4с** (`diag1.log`) | **~20.4с** (`diag_after_fix.log`) |

реального; на настоящем телефоне с 60кадр/с эта стройка должна занимать вплотную к сырому

чинятся в той функции, где реально возникли», но НЕ значит «чинить заодно всё найденное»)):
`tuneMechanicsV43()` (`tycoon-v116.html:19182`) переопределяет `constructionDuration` на
формулу без более позднего (`v80`, `tycoon-v116.html:31191`) множителя `×1.62`/зажима
`[5.1,10.4]` — и делает это ПОЗЖЕ по факту исполнения, потому что вызывается из
`runV43Polish()` через `DOMContentLoaded`+`setTimeout(...,80)` (`tycoon-v116.html:19221`), то
есть уже ПОСЛЕ того, как все синхронные `<script>`-блоки документа (включая v80, который
физически ниже по файлу) успели выполниться. Из-за этого «более длинная база, чтобы бригада
успела дойти» из v80 никогда фактически не действует ни для одной стройки, ни на старом, ни на
новом сейве — подтверждено живым вызовом `constructionDuration(0,1,false)` в консоли браузера:
возвращает `2.75` (v43), а не `clamp(2.75×1.62, 5.1, 10.4)=5.1` (v80). Это не влияет на
корректность фикса выше (сам фикс проверен вживую на реальном `constructionDuration`, а не на
теоретическом), но объясняет, почему даже штраф v80 «ждать бригаду» в принципе избыточно
суров относительно короткой v43-длительности. Чинить эту более широкую нестыковку — отдельная,
более рискованная правка балансировки ВСЕХ построек на ВСЕХ сейвах, вне узкого скоупа этого
захода («тюнинг константы для первых 1-2 зданий»); оставляю как честную находку для будущего
прохода, а не тащу новую механику/широкую перебалансировку сюда.

### 1. `nextActionableTargetV117()` — приоритетная функция «что делать дальше»

`tycoon-v116.html:8353` (сразу после `nextBuildFallbackAvailable()`, рядом с
`currentGuidanceTarget()`). Порядок проверки:

1. Ближайший купленный, но не подключённый дорогой дом (`manualRoadModeV116` +
   `manualRoadStagesV116`, позиция — `stageRoadEndpointV367(b.index)`, та же точка, где
   канонический рендерер обрывает асфальт) → `{type:'road'}`.
2. `currentPad` (следующий дом/апгрейд), но только когда он ДЕЙСТВИТЕЛЬНО доступен прямо сейчас
   (`canAffordStage(stageIndex) && constructionSlotAvailable()`) → `{type:'stage'}`.
3. Пэд «Построить завод», если он ещё не построен и по деньгам доступен
   (`!industrialZoneBuiltV116 && canPayResources(INDUSTRIAL_ZONE_PAD_COST_V116)`) →
   `{type:'factory'}`.
4. Иначе `null` (мягкое состояние «нечего делать прямо сейчас» — компас/подсветка/стрелка
   просто гаснут, без «утешительного» текста поверх экрана, что тоже соответствует правилу
   «только кружочки»).

**Осознанное отклонение от буквального порядка задания** (разрешено самим заданием: «adjust based
on what you find»). Задание перечисляло порядок «дорога → завод → дом», но на самом первом кадре
пустого мира и дом (`STAGES[0]`, 50💰, без материалов) и завод (`INDUSTRIAL_ZONE_PAD_COST_V116`,
150💰) уже доступны одновременно на стартовые 300💰 — при буквальном порядке подсветка/стрелка
показывали бы на завод РАНЬШЕ первого дома, что прямо противоречит собственному прогресс-плану
`VISION.md` («Первый дом ... Дошёл пешком до промзоны»). Поэтому проверка «доступного дома»
стоит между дорогой и заводом: как только у следующего дома не хватает материалов (единственная
причина, по которой завод вообще становится актуальной целью), `canAffordStage()` честно вернёт
`false`, и приоритет естественно перейдёт на завод — без единого хардкода на номер стадии.

`currentGuidanceTarget()` (`tycoon-v116.html`, была/осталась единственной точкой, из которой
берут данные и `#compass` — стрелка-край-экрана, existing с более раннего захода, — и

### 5. Найденный и исправленный баг: TDZ-обрыв всего скрипта на пустом мире

Первая версия правки вызывала `spawnFactoryPadMarkerV117()` безусловно на верхнем уровне рядом с
`if(industrialZoneBuiltV116) buildSawmillScenery();` (`tycoon-v116.html:3242` в старой редакции) —
то есть в тот же момент, что и остальные v116-гейты бутстрапа. Живой прогон немедленно поймал
регресс: `boot.test.mjs`, `hud.test.mjs` и `nav-pads.test.mjs` упали с `ReferenceError: player is
not defined` внутри `page.evaluate` — то есть глобальная переменная `player`, объявленная тысячами
строк ниже в том же корневом `<script>`, вообще не инициализировалась на пустом сейве.

**Причина** (найдена вживую, `scratchpad/guidance116/debug1.mjs` — прямой дамп
`page.on('pageerror')`): первая же реальная ошибка в списке —
`"Cannot access 'factoryPadMarkerV117' before initialization"`. `factoryPadMarkerV117` — это
`let`-переменная, объявленная ВНУТРИ функции `spawnFactoryPadMarkerV117()` дальше по файлу
(`tycoon-v116.html:8150`), но верхнеуровневый вызов на строке 3242 срабатывал ДО того, как
исполнение скрипта дошло до этой строки — то есть до того, как binding вообще был инициализирован
(temporal dead zone). Непойманное исключение прямо на верхнем уровне `<script>`-блока обрывает
всё оставшееся исполнение этого блока — тот самый класс бага, о котором сам файл уже
предупреждает в соседних комментариях («uncaught ReferenceError there aborts the rest of this
whole `<script>` block»). Из-за этого `player`, `CITY_DISTRICTS`, `cityWorldRuntime`,
`livingCityRuntime`, `baseRuntime`, `serviceVehicles` и десятки других глобальных переменных,
объявленных ниже по файлу, просто никогда не создавались на пустом сейве — список
`pageerror`/`console.error` в `debug1.mjs` показывает лавинообразный каскад из ~30 разных
`ReferenceError`/`Cannot access before initialization` по всей остальной части бутстрапа.

**Фикс** (`tycoon-v116.html`, тот же принцип: не новый слой, а перенос вызова в безопасную
точку): вызов `spawnFactoryPadMarkerV117()` убран с верхнеуровневой позиции рядом с
`buildSawmillScenery()` и перенесён в конец файла, сразу после `load();` (`tycoon-v116.html:18890`),
где все `let`/`const`-биндинги всего скрипта уже гарантированно инициализированы (это тот же
самый принцип, по которому в файле уже давно вызывается `ensureInfrastructureStateV37()` и
`initializeGuideRewardsV351()` сразу после `load()` — не самое начало файла). На старой позиции
оставлен подробный комментарий-предупреждение, чтобы будущий агент не восстановил тот же баг.

**Тест до фикса**: `scratchpad/guidance116/debug1.mjs` на пустом `localStorage` —
`pageerror: Cannot access 'factoryPadMarkerV117' before initialization` первым в списке, далее
~30 каскадных ошибок; `npm test` — 4/7 (`boot.test.mjs`/`hud.test.mjs`/`nav-pads.test.mjs` FAIL).

**Тест после фикса**: `scratchpad/guidance116/debug1.mjs` — `errors: []`, 0 ошибок на пустом
сейве; полный `npm test` (8 файлов, добавлен `tests/guidance.test.mjs`) — **8/8 PASS**.

### 6. Постоянный тест `tests/guidance.test.mjs`

7 проверок, каждая — живое состояние страницы, не самоаудит:
1. Пустой старт → цель `type:'stage'` (первый дом), НЕ `'factory'`, хотя завод тоже уже

   при этом честно откатывается на существовавшую раньше цепочку «иди к дереву» — ноль регрессии

6. Всплывающий текст — спавнится на реальном событии (постройка дороги), исчезает сам после

   нагрузкой, так что `requestAnimationFrame`-цикл игры накапливает игровое время намного
   медленнее реального; тот же приём уже используют другие тесты сессии для таймеров стройки).
7. Старый сейв (`manualRoadModeV116:false`, `industrialZoneBuiltV116:true`) — обе новые ветки не
   срабатывают, цель — тот же `currentPad`, что и раньше.

### 2. Расследование `[road union] Error: Open road union contour` — найдено и исправлено

Несколько агентов этой сессии отмечали это сообщение как повторяющееся на ~5% перезагрузок,
воспроизводимое 1-в-1 на более ранних коммитах — то есть не регресс этой сессии — но никто не
докопался до причины. Раз уж строился постоянный набор тестов, разобрались до конца.

**Метод**: живая инструментация (не самоаудит) — временная копия файла в `scratchpad/` с
логированием прямо внутри `roadUnionContours()` (причина обрыва цепочки, все граничные рёбра,
полный `userData`/родительская цепочка каждого меша-«тротуара») плюс отдельные логи-обёртки на
каждую функцию, которая может владеть `cityWorldRuntime.transportAccessRoads`
(`refreshTransportAccessRoads` — все версии, `rebuildServiceRoadsV66`, `installStableOwners`,
`addPersistentDeckV116`). Прогнано ~150 живых перезагрузок Playwright + iPhone 13 на старом сейве
из задания через несколько итераций гипотез.

**Причина**: у `refreshTransportAccessRoads` в файле оказалось ТРИ последовательных определения
(конвенция «выигрывает последнее по порядку в файле» — но это верно только для того, что видит
код, который вызывает функцию ПОСЛЕ того, как все три уже отработали; на самом деле любой РАННИЙ
вызов по имени резолвится в то, что переменная держит В ЭТОТ МОМЕНТ):
1. `function refreshTransportAccessRoads()` (`:11975`, простой `addRoadSegment()`-рендер,
   безопасный — см. ниже),
2. `refreshTransportAccessRoads=function(){...}` (было `:28919`, на `renderNetwork59()`+
   `addIntersection59()` — «красивый», с настоящими скруглёнными T/X-заливками),
3. `refreshTransportAccessRoads=function(){return rebuildServiceRoadsV66();}` (`:30109`) →
   позже перезаписывается в `refreshTransportAccessRoads=()=>syncServiceRoads()` (`:35360`,
   «стабильные владельцы» v113, финальная версия на всю оставшуюся игру).

Живой каскад инициализации дорог v36.5/v36.6 (`setTimeout(...,120)`/`setTimeout(...,180)`, до сих
пор в файле, оба вызывают `refreshTransportAccessRoads()` по имени) **подтверждённо** иногда
успевает выстрелить ДО того, как второй и третий слои успели переопределить переменную — прямое
логирование поймало это на каждом из 7 пойманных сбоев за один прогон: `refreshTransportAccessRoads`
в момент срабатывания таймера резолвился именно во ВТОРОЕ («красивое») определение, причём оба
вызова (`:16194`/`:16261`) стабильно попадали в него. Это чистая гонка по реальному времени: при
достаточно тяжёлой загрузке страницы (конструирование сцены, swiftshader-рендер) 120/180мс
таймеров может истечь раньше, чем однопоточный синхронный разбор оставшегося HTML/JS доберётся до
строк `:30109`/`:35360` — измерено живьём, в пойманных случаях таймеры реально стреляли на
t≈2.2–3.0с после навигации, а не через номинальные 120/180мс.

Второе (`renderNetwork59`) определение вызывает `addIntersection59()` для настоящей T/X-заливки
перекрёстков графа `serviceAccessGraph()` — и у этого графа узел `metalBypass` — честный, ПОСТОЯННО
существующий T-перекрёсток на три ветки (`clusterGate`, `concreteBypass`, `metalHome`), где
`clusterGate` и `metalHome` уходят от узла практически в одном направлении (не случайность позиций
— это так задумано геометрией промзоны). `addIntersection59()`/`addRoadDeck59()`'s обрезка по
`jointHalf59()` не рассчитана на «прищепленный» T с двумя почти-параллельными направлениями и
оставляет ~0.2-юнитный висящий обрывок границы асфальта прямо в этом узле — тот самый
неоднозначный («открытый») контур, на котором `roadUnionContours()` спотыкается. Воспроизведено
байт-в-байт идентично (те же две граничные вершины: `(-38.8084,-7.97)`↔`(-38.6084,-7.97)`) на
каждом из 7 пойманных сбоев подряд — то есть не шум/дрейф плавающей точки, а один и тот же
детерминированный геометрический дефект, просто достигаемый недетерминированной по времени гонкой.

Отдельно найден и тоже устранён (хоть и не он был причиной именно этой ошибки — проверено:
воспроизводится байт-в-байт одинаково с ним и без него) более простой, не связанный с гонкой по
времени дефект того же класса в этом же определении: узлы `concreteBay`/`metalBay` — точки
погрузки, лежащие ПРЯМО на линии основного коридора (не боковая ветка), и второе определение (в
отличие от `rebuildServiceRoadsV66()`, у которой уже стоит явное исключение с комментарием «drawing
their subset segment again would stack asphalt») рисовало их как отдельный сегмент поверх основной
дороги. Исключение добавлено и в первый (`:11975`) хостед-стаб — той же одной строкой, что уже
есть в `rebuildServiceRoadsV66()`.

**Фикс** (в той же функции, где реально возникает — не новый патч-слой): второе, «красивое»
определение (`:28919`) удалено целиком. Оно было полностью избыточным — единственная причина, по
которой оно когда-либо реально выполнялось, — именно эта гонка; в штатном сценарии его тело
подменялось третьим определением за миллисекунды. После удаления реассайна имя
`refreshTransportAccessRoads` на время того же гоночного окна продолжает держать значение первого,
безопасного хостед-стаба (`:11975`, простой `addRoadSegment()`-рендер — обрезает каждый сегмент
независимо, `addIntersection59()` не вызывает вообще, так что «прищепленный T» ему физически не
угрожает), а затем как и раньше корректно переписывается третьим слоем. Экрана пользователь в
норме не видит вообще — окно перезаписывается за доли секунды, — но нового пустого места в коде не
появилось: одна функция удалена, ни одного нового патч-слоя не добавлено, число `<script>`-блоков
осталось тем же (65).

**Тестирование фикса**: `node --check` по всем 65 блокам — 0 ошибок (то же число, что до фикса —
фикс убрал функцию, а не добавил слой). Полный набор из 7 файлов (6 исходных + новый
`tests/road-union.test.mjs`, см. ниже) — `npm test` → **7/7 пройдено** на исправленном файле, ни
одной регрессии. Отдельно, живьём (то же окружение, тот же старый сейв, тот же метод измерения,
что нашёл баг):
- **До фикса** (тот же коммит, до этого захода, три независимых прогона): 4/40, 7/40 и 12/49
  (третий прогон упал на своём 50-м шаге из-за отдельного, несвязанного крэша Chromium под
  нагрузкой — не баг игры, посчитано по успешно завершённым итерациям) — диапазон **~10–25%** на
  разных прогонах, то есть даже выше, чем «~5%», о которых сообщали предыдущие агенты (вероятно,
  из-за более тяжёлой/шумной среды CI в этой сессии, что и объясняет саму гонку по времени).
- **После фикса**: **0/50** (кандидат-версия) и **0/60** (финальная версия, ровно закоммиченный
  файл) — итого **0 срабатываний на 110 перезагрузок** тем же методом, который до фикса стабильно
  давал десятки срабатываний на сопоставимой выборке.
- Постоянный регресс-тест `tests/road-union.test.mjs` добавлен в новый набор — по умолчанию 20
  живых перезагрузок того же старого сейва, 0 срабатываний ожидается; при регрессии падает с
  указанием на то, что чинил этот заход (переменная `ROAD_UNION_ITERATIONS` регулирует размер
  выборки для более уверенной проверки при необходимости).

### 4. Обмен ресурсов — новая механика, курс и почему именно такой

Обмена раньше не было ни в одной из 6 систем — это честно новая фича, как и просил пользователь.
Курс (`MARKET_EXCHANGE_VALUE_V116`, `:9709`) выведен из уже существующей экономики, а не выдуман:

- В `STAGES` (`:1283`) для тарифов Офис→Бизнес-центр→Небоскрёб→Империя (единственные 4 строки,
  где все три ресурса требуются одновременно на сопоставимых по деньгам этапах) суммарные
  требуемые количества — **80 досок : 56 бетона : 29 металла**. То есть игра уже сегодня просит
  в ~2.76 раза больше досок, чем металла, и в ~1.43 раза больше бетона, чем досок, ради того же
  самого этапа по деньгам — а значит (переворачивая соотношение) единица металла «стоит» в
  экономике игры примерно в 2.76 раза больше единицы досок, единица бетона — примерно в 1.43 раза
  больше единицы досок. Округлено до чистых чисел: **доски : бетон : металл = 1 : 1.5 : 3**.
- Подтверждается косвенно и формулой `opsCost()` (`:9232`, используется для апгрейдов
  автопарка/базы): доски там растут линейно с уровнем (`2n`), а бетон/металл — фиксированные
  маленькие числа (`2`/`1`) вне зависимости от уровня, то есть та же экономика уже считает
  металл/бетон куда «дороже за единицу», чем доски — без противоречия с курсом выше.
- Курс в деньги (`MARKET_SELL_PRICE_V116 = {planks:8, concrete:12, metal:24}`, `:9713`) — **не**

  намеренно консервативная оценка, сохраняющая то же соотношение 1:1.5:3, но подобранная так,

- Комиссия рынка 10% (`MARKET_EXCHANGE_FEE_V116=0.9`) — на каждый обмен, включая деньги, чтобы
  цикл A→B→A (или ресурс→деньги→ресурс) всегда терял часть ценности, а не был бесплатным
  арбитражем.

9 направлений обмена (`MARKET_EXCHANGE_OFFERS_V116`, `:9715-9725`), каждое — фиксированный ввод

### 2. Дороги вручную — один кружок «Дорога» на каждый купленный дом без дороги

**Отклонение от чернового наброска задания, зафиксировано честно** (задание явно разрешает
использовать собственное суждение и просило задокументировать расхождение): вместо
дробления дороги на кружки-по-сегменту с отдельными развилками на поворотах, каждый КУПЛЕННЫЙ,
но ещё не подключённый дом получает ОДИН кружок «Дорога» на конце своего подъезда
(`stageRoadEndpointV367(i)` — та же точка, где канонический рендерер и так обрывает асфальт).
Нажатие достраивает ВЕСЬ маршрут от хаба до дома целиком (со всеми поворотами/T-образными
слияниями с уже существующей сетью), а не один прямой отрезок. Причина упрощения: дорожная
система (`v86-canonical-stage-roads`/`v113-stable-road-blueprint`) устроена как «полный
посчитанный маршрут на дом», а не как склеиваемые из отдельных прямых кусков сегменты — сама
история этого файла (см. `ROADS_V116_NOTES.md`, восьмой заход) — это восемь раундов тонких
регрессий именно в этой системе; резать её на ручные под-сегменты означало бы переписывать
рендерер, а не «менять только триггер», что прямо запрещено заданием. Причина, почему это не
обедняет геймплей: результат для игрока идентичен формулировке «наступил на кружок — дорога
сама протянулась и красиво влилась в существующую сеть», просто гранулярность «один дом = один
кружок», а не «один поворот = один кружок». `VISION.md` обновлён (раздел «Дороги») с пометкой
об этом отличии от прежнего черновика.

**Механизм** (переиспользует ровно тот же паттерн, что 9-й заход завёл для district/project
пэдов через `nearestManualTargetV53()`/`#actionPrompt`/`#actionBtn` — не изобретён новый):
- `manualRoadModeV116` (`:~973`) — `true` только для сейва, у которого при первой загрузке вообще
  не было `SAVE_KEY` (не путать с `industrialZoneBuiltV116` — это две независимые пометки: один
  флаг про завод, другой про то, что дороги в этом сейве вообще ручные).
- `manualRoadStagesV116` — `Set` индексов домов, чья дорога реально построена игроком;
  персистится в сейве как массив.
- `activeStageIdsV92()` (`tycoon-v116.html:32196`, единственное место, откуда канонический
  рендерер узнаёт «какие дома active») — при `manualRoadModeV116` фильтрует свой обычный
  результат (`stageIndex`+`buildings[].index`, БЕЗ ИЗМЕНЕНИЙ) по `manualRoadStagesV116`. На
  обычном сейве (`manualRoadModeV116` false) эта фильтрация вообще не выполняется — функция
  возвращает ровно то же, что и раньше этого захода, побайтово.
- `nearestManualTargetV53()` получил новый тип кандидата `'road'` — по одному на каждый
  `buildings[]`-дом без записи в `manualRoadStagesV116`, позиция — `stageRoadEndpointV367(i)`.
- `buildManualRoadStageV116(i)` (`tycoon-v116.html:8113`) добавляет `i` в множество и вызывает
  `refreshStageRoadsV367()` — тот же самый живой владелец `syncStageRoads()`

### Что на самом деле открывал каждый пэд

`buildWorldNavPadV362()`/`WORLD_NAV_CONFIG_V362` (`tycoon-v116.html`, было ~строка 14966) — не
3, а **10** пэдов, сгруппированных единым кластером у спавна (`WORLD_NAV_PAD_LAYOUT_V362`), из
которых на скриншотах пользователя видны только уже разблокированные на его стадии игры
(«Компания», «Город», «Команда», «Автопарк» — остальные шесть, «База»/«Проекты»/«Тендеры»/
«Операции»/«Мета»/«Бонусы», открываются позже по `stageIndex`). Каждый пэд не делал ничего, кроме
`document.getElementById(cfg.triggerId||cfg.buttonId).click()` — то есть являлся 3D-дублем уже
существующей 2D-кнопки, которая открывает одну из 9 существующих 2D-панелей-оверлеев
(`systemsOverlay`/`cityOverlay`/`staffOverlay`/`fleetOverlay`/`baseOverlay`/`projectsOverlay`/
`tendersOverlay`/`operationsOverlay`/`metaOverlay`/`bonusOverlay`). Классический анти-паттерн
из прямого правила `VISION.md`: «Всё прокачивается через круглые кнопки на траве... Никаких
вкладок, меню-списков и плашек поверх экрана» — кружок, единственная работа которого — открыть
другое меню, это не действие на месте, а портал в меню.

Разбор по каждому пэду и что с ним сделано:

1. **«Компания» (`systems`, значок ☰)** — 100% дубликат уже существующей постоянной иконки
   `#systemsBtn` в правом верхнем углу HUD (тот же `triggerId`, буквально тот же DOM-элемент,
   на который кликает пэд). Удалён без замены — ничего не потеряно, иконка в углу остаётся
   ровно как раньше.
2. **«Город» (`city`, «Районы»)** — не сводится к одному месту (сама панель `cityOverlay` — это
   апгрейд районов + участки + гражданские здания + дороги/освещение + политика, полноценный
   под-экран). НО конкретное действие «поднять уровень района» (`upgradeCityDistrict()`) уже
   привязано к 4 реальным фиксированным позициям (`CITY_DISTRICTS[].pos`), и в мире у каждого
   района уже стоит физический маркер (`createDistrictHub()`, диск+вывеска с уровнем/условием
   разблокировки) — просто он был чисто декоративным (не интерактивным). Сделан интерактивным:
   стоя рядом с хабом своего района, апгрейд теперь запускается напрямую (см. «Фикс» ниже) — по
   прямому указанию задания («если 3 района — у каждого своя площадка на краю района, а не общее
   меню Районы»). Более глубокая под-панель (участки/гражданские здания/политика) остаётся
   доступной как раньше, через `#systemsBtn → Город`, вне рамок этого захода.
3. **«Команда» (`staff`, «Люди»)** — **НЕ перенесено, оставлено как есть** (обоснование ниже).
4. **«Автопарк» (`fleet`)**, **«База» (`base`)**, **«Тендеры» (`tenders`)**,
   **«Операции» (`operations`)**, **«Мета» (`meta`)**, **«Бонусы» (`bonus`)** — **НЕ перенесены,
   оставлены как есть** (обоснование ниже).
5. **«Проекты» (`projects`, «Рост»)** — 3 спецпроекта (`SPECIAL_PROJECTS`: парк/логистический
   центр/штаб-квартира), у каждого уже есть фиксированная реальная позиция (`.pos`) и, что

   проектов раньше вообще не было никакого физического присутствия в мире — их можно было

### Почему «Команда»/«Автопарк»/«База»/«Тендеры»/«Операции»/«Мета»/«Бонусы» не переехали на землю

Осознанное решение, а не недосмотр — каждый честно проверен на «есть ли одно реальное физическое
место»:

- **Команда** (`STAFF_CONFIG`: бригада строителей/водители/инженеры/прорабы) — 4 абстрактных
  ОБЩЕКОМПАНЕЙСКИХ множителя (например, инженер даёт `+6% ко ВСЕМ ресурсам`, прораб —
  `+5% к контрактам и +2.5% ко ВСЕМ рабочим`). У них нет одного корректного физического места:
  прикрепить «нанять инженера» к конкретному зданию (лесопилке, базе...) означало бы соврать —
  эффект не локальный. Это не тот же случай, что уже существующие локальные пэды апгрейда
  (`FIELD_UPGRADE_CONFIGS` — «Мотор лесопилки», «Распил древесины» и т.д., они честно стоят
  у лесопилки и влияют только на неё).
- **Операции** (`operationsOverlay`) — вообще не апгрейд-меню, а живая панель управления очередью
  строек (приоритет каждой активной стройки, ручной reorder очереди кнопками ↑/✕) — по своей
  природе не сводится к «дошёл до места — нажал», это сравнение/управление несколькими
  одновременными объектами сразу.
- **Мета** (`metaOverlay`, `V30_META_UPGRADES`) — престиж-дерево перманентных бонусов за очки
  престижа, абстрактно, без физической локации по построению механики.
- **Автопарк**/**База**/**Тендеры**/**Бонусы** — тоже общекомпанейские (типы техники, модули
  базы, контракты-квесты, разовые rewarded-бонусы) без единой честной физической точки;
  технически могли бы быть насильно приколоты к базе/гаражу, но это отдельная, более крупная
  фича (новая пэд-геометрия под 4+ систем, тонкая настройка коллайдеров/переводов) — сознательно
  оставлено вне рамок этого захода, а не сделано наспех. Задокументировано здесь, чтобы решение
  было видно, а не потерялось.

Все семь остаются доступны ровно как до этого захода — через `#systemsBtn` (правый верхний угол)
→ список разделов `systemsOverlay`, который существовал ДО кластера world-nav-пэдов (`v30.1`,
задолго до `v36.2`) и не менялся.

### Фикс

**Удаление кластера** (`tycoon-v116.html`, было ~строки 14966–15098): `WORLD_NAV_CONFIG_V362`,
`WORLD_NAV_PAD_LAYOUT_V362`, `worldNavUnlockedV362()`, `worldNavLabelV362()`,
`buildWorldNavPadV362()`, `createWorldNavPadsV362()`, `updateWorldNavPadsV362()`,
`worldNavBlockedByPriorityV362()`, `anyOverlayOpenV362()`, `nearestWorldNavPadV362()`,
`openWorldNavPadV362()`, `syncWorldNavPromptV362()` и его собственные дублирующие
keydown/click-слушатели — удалены целиком (не спрятаны CSS-правкой, как в прошлом заходе для
quest-стека: здесь удаляется не просто рендер, а вся система вместе с данными, полностью
замещённая ниже). Заодно найден и обезврежен **реальный краш**, который иначе получился бы:
загрузочный `setTimeout` (тот же файл, было ~строка 15161) вызывал `createWorldNavPadsV362()` и
`syncWorldNavPromptV362()` ПЕРВЫМИ внутри общего `try{}` вместе с `refreshLivingDistrictStreets()`/
`refreshArterialRoads()`/`refreshDistrictAccessRoads()`/`refreshTransportAccessRoads()`/
`refreshDrivewaysV35()` — если бы удаление функций не сопровождалось удалением этих двух вызовов,
первая же `ReferenceError` при загрузке обрывала бы `try` и все пять дорожных refresh-вызовов
после неё вообще не выполнялись бы. Оба вызова убраны из этого `setTimeout`, остальные пять —
не тронуты. Также удалена мёртвая `createIconSpriteV36()` (существовала исключительно ради
иконок удаляемых пэдов, ничего больше её не вызывало — подтверждено grep'ом).

**Районы — прямая интерактивность** (`nearestManualTargetV53()` + блок обработки
`interactRequested` + `installManualPromptV46()`, тот же файл): для каждого `CITY_DISTRICTS[]` с
`districtUnlocked(cfg) && districtLevel(cfg.id)<3` считается расстояние до `cfg.pos` (реальная
позиция уже существующего `createDistrictHub()`) и добавляется кандидатом `{type:'district',...}`
в тот же общий arbitration-список, что уже используют апгрейды зданий/полевые пэды — тот же
компонент, тот же радиус (`PAD_TRIGGER_RADIUS`), никакого нового паттерна взаимодействия. Нажатие
рядом с хабом района напрямую вызывает `upgradeCityDistrict(cfg.id)` (та же функция, что раньше
дёргалась из кнопки внутри `cityOverlay` — переиспользована как есть, не продублирована), с тем же
`insufficientShown`-дебаунсом на нехватку ресурсов, что и у остальных пэдов.

**Спецпроекты — маркер вакантного участка** (`refreshSpecialProjectWorld()`,
`createSpecialProjectAvailableMarker()`, тот же файл): для каждого разблокированного, ещё не
начатого и не завершённого `SPECIAL_PROJECTS[]` на его собственной `.pos` теперь стоит небольшой
диск с иконкой и вывеской (имя + стоимость) — без коллайдера (в отличие от завершённого
ландшафтного объекта/активной стройплощадки), чтобы к нему можно было подойти вплотную, как к
любому обычному пэду. Тот же `nearestManualTargetV53()` добавляет кандидата `{type:'project',...}`,
нажатие вызывает уже существующий `startSpecialProject(p.id)` напрямую. Маркер пересобирается
раз в 700мс лёгким `setInterval` (идемпотентно, только проверки `Map.has()` — безопасно дёргать
каждый тик) — так же, как уже существующий интервал в 650мс пересобирает вывески хабов районов;
это гарантирует, что вновь разблокированный проект (по мере роста `stageIndex`) получает маркер
без перезагрузки страницы.

### 1. Зигзаг на stage-дороге — настоящий регресс в системе владения дорогами, найден и исправлен

**Что видно на скриншоте пользователя**: не диагональный обрубок (как в третьем заходе), а
локальный «зубец» прямо у стыка с одним из домов — дорога делает короткий шаг вбок и обратно
ровно там, где от общего «ствола» ответвляется дорога к другому дому, при этом ДАЛЬШЕ по тому же
стволу виден совершенно гладкий, правильно скруглённый поворот. Это разница в КАЧЕСТВЕ отрисовки
одного и того же класса стыков в одном и том же кадре — прямая улика, что часть сети рисуется
одним (хорошим) владельцем, а часть — другим (упрощённым).

**Причина, найдена вживую** (`tycoon-v116.html`, метод — прямой live-вызов внутренних API, а не
самоотчёт): канонический владелец сети stage-дорог, `v86-canonical-stage-roads`
(`window.__TYCOON_STAGE_ROADS__`), строит настоящие скруглённые повороты и Т/Х-заливки
(`addCorner()`/`addJunction()`, `plan()`+`atomic()`+`nodes()` внутри `makeGroup()`) — но эта
дорогая, «честная» пересборка запускается ТОЛЬКО из `fullSync()` (`v84-road-collision-unification`,
внутри), за гвардом по `generation` (это тот самый гвард из шестого захода, который остановил
пересборку сети на каждый холостой тик). `fullSync()`, в свою очередь, навешен только на
`refreshBaseWorld()`/`refreshSpecialProjectWorld()` — то есть на апгрейды базы/спецпроекты. Но
обычная постройка домов игрока (`purchaseCurrentPad()` → `refreshInfrastructureWorldV37()` →
`refreshStageRoadsV367()`) их вообще не вызывает — она идёт через ДРУГОЙ, более поздний слой,
`v113-stable-road-blueprint`, чья `syncStageRoads()`/`appendStageV116()` **дозаписывает только
прямые куски асфальта** («append-only», без единого вызова `addCorner()`/`addJunction()` — это
задокументированный, сознательный компромисс шестого захода ради производительности, см.
`ROADS_V116_NOTES.md`). Итог: канонический «честный» пересчёт с скруглением фактически выполняется
**один раз**, на загрузке, при нуле построенных домов (см. `const boot=()=>fullSync(true);` внутри
`v84`) — и никогда больше за всю обычную игру. Live-проверка подтвердила это дословно: после
постройки всех 10 домов через нормальный `purchaseCurrentPad()`,
`window.__TYCOON_STAGE_ROADS__.audit().network` показывал `stageIds:[]`/`nodes:0` (застрял на
до-домовом состоянии), а ручной вызов `window.__TYCOON_V61_AUDIT__.refresh()` (тот же самый
внутренний «честный» rebuild v86, вызванный напрямую) мгновенно чинил сеть до `CORNER:6,T:6,X:1` —
то есть код скругления рабочий и правильный, просто не вызывается штатным путём. Отдельно
проверено (и отброшено) — что виноват сам generation-гвард: `window.__TYCOON_V83_COLLISIONS__`,
чей registry и питает `sigNow()` этого гварда, ни разу не получает 'building'/'construction' записи
для stage-домов игрока вообще (только фиксированные индустриальные статики) — то есть даже прямой
вызов `window.__TYCOON_V84_ROADS__.refresh()` не помогал, гвард всегда видел «без изменений».

**Фикс** (`syncStageRoads()`, `tycoon-v116.html`, `v113-stable-road-blueprint`, тот же владелец
точки вызова, без нового слоя): когда `appendStageV116()` реально дописал асфальт для НОВОЙ
стадии (`added===true` — тот же флаг, что уже стоит на страже остальных пост-обработок в этой же
функции — маркировка/коллизии/трафик), дополнительно вызывается
`window.__TYCOON_V61_AUDIT__?.refresh?.()` — тот же самый честный rebuild v86 напрямую, в обход
сломанного registry-based гварда `fullSync()`. Это безопасно и ограничено по частоте: ветка и так
выполняется только при `added===true`, то есть один раз на реальную новую стадию (10 раз за игру),
никогда на холостых тиках — на них `appendStageV116()` для уже добавленных стадий не находит
ничего нового (`runtime.stagePaths.has(i)` истинно), `added` остаётся `false`, и новый вызов не
срабатывает.

**Тест до фикса** (`scratchpad/ui2_116/test_fullsync2.mjs`, 10 домов через нормальный
`purchaseCurrentPad()`): `window.__TYCOON_STAGE_ROADS__.audit().network` = `stageIds:[],raw:0,
segments:0,nodes:0,kinds:{}` — сеть застряла на до-домовом снимке; сравнение
скриншотов (`scratchpad/ui2_116/road_after_fix_1.png` до правки не снималось отдельно, но
геометрически идентичный «зубец» воспроизведён и измерен вживую при том же построении домов).

**Тест после фикса** (тот же скрипт, тот же сценарий постройки): без единого ручного вмешательства
`window.__TYCOON_STAGE_ROADS__.audit().network` = `stageIds:[0..9],raw:29,segments:22,nodes:23,
kinds:{X:1,END:10,T:6,CORNER:6}` — то есть канонический честный rebuild со скруглением теперь
запускается автоматически на каждую новую стадию. Скриншоты
`scratchpad/ui2_116/road_after_fix_1.png`/`road_after_fix_2.png` — гладкие скруглённые
развязки/повороты у только что построенных домов, без единого зубца. Регресс на холостом простое
проверен отдельно (см. раздел «Тестирование» ниже) — новый вызов не реинтродюсит бага шестого
захода («пересборка сети на каждый холостой тик»).

### 2. «Белые кружки» — подтверждённый декоративный элемент world-nav-пэдов, убран

Живая идентификация (по инструкции — раскрутка/скриншот/сопоставление проекции экрана с реальным
мешем сцены, НЕ угадывание): пользовательский белый овал под подписанными кнопками
«Компания»/«Город» (и всеми остальными world-nav-пэдами, `WORLD_NAV_CONFIG_V362`) — это
`TorusGeometry(1.48,.11,14,28)` внутри `buildWorldNavPadV362()` (`tycoon-v116.html`, было ~строка
15006), собственный цвет `0xe6edf7` (обычное состояние) / `0xffefc7` (рекомендованное) — оба почти
белые вне зависимости от цвета самого пэда (`cfg.color`, у каждого раздела свой). Подтверждено
вживую: `worldNavRuntimeV362.pads[i].ring.material.color.getHexString()` неизменно `e6edf7`/
`ffefc7` для ВСЕХ разделов (Компания — серо-синий `6f7f95`, Город — зелёный `4fb181` и т.д.) —
то есть это не оттенок цвета пэда, а отдельный, всегда почти-белый декоративный «воротник» вокруг
диска. НЕ спутан с другими кольцевидными декалями в файле — проверено и отброшено: плазовые
`RingGeometry`-декали (`GROUND_HALF*...`), «спицы» центральной площади (`addPlazaSpoke`, см. пункт
ниже — другой файл-строка, другая причина) и `guideWorld.ring` (жёлтый маркер цели квеста,
`0xffd479`, с отдельной подписью «ЦЕЛЬ») — визуально и по коду не совпадают с найденным.

**Фикс** (`buildWorldNavPadV362()`/`updateWorldNavPadsV362()`, тот же единственный владелец,
без нового слоя): меш `ring` и все обращения к нему (создание, `userData`/возвращаемый объект,
покраска в `updateWorldNavPadsV362()`) удалены целиком. Подписанная кнопка (тёмный значок с
иконкой) и её цветной диск (`disc`, реально несёт цвет раздела) остаются — это тот самый «хороший»
элемент, который пользователь просил не трогать (см. пункт 3 ниже).

**Тест до/после** (`scratchpad/ui2_116/ring_ORIGINAL_unfixed.png` vs `ring_FIXED.png`, тот же live
`stageIndex=4`, тот же набор разблокированных пэдов): до — под каждым подписанным значком видно
явное сплошное белое кольцо (донат/тор) вокруг цветного диска; после — кольцо полностью исчезло,
остаётся только собственный, спокойный по цвету диск раздела. `hasRing:false` подтверждено
программно для всех видимых пэдов.

**Отдельно найден и НЕ ТРОНУТ второй, похожий, но независимый декоративный элемент**: «спицы»
центральной гражданской площади (`addPlazaSpoke()`, `fullEnvironmentAuditPass()`,
`tycoon-v116.html`) — короткие декоративные дорожки с кремовым (`0xe6dcc8`/не чисто-белым)
торцевым «пятачком» (`endCap`, `CircleGeometry(width*0.56,18)`), расходящиеся от центрального хаба
(`innerPlaza`, тан-плитка 9×9). Это НЕ то, на что жаловался пользователь (другой цвет, другая
геометрия, другое расположение — по мнению задания, ложный кандидат, upheld отдельной живой
идентификацией), но по ходу расследования вскрылся реальный, самостоятельный баг: `innerPlaza`

`refreshStaticUrbanVisibilityV37()`), а вот спицы/торцевые пятачки — нет, у них вообще нет такого
условия видимости, поэтому в начале игры (0 районных дорог, как на скриншотах пользователя) они
висят в воздухе поодиночке в чистом поле безо всякой связи с площадью, которой ещё не видно. Не
исправлено в этом заходе — не тот баг, который пользователь просил починить, и трогать
видимость декора площади отдельно от самого явного «кольца» посчитали риском не по делу; оставлено
задокументированным на будущее.

## 2026-09-26 (седьмой заход) — Индустриальный кластер перенесён в отдельную зону, конвейер де-элевирован, перекрёстки «дозированы»

Самый крупный заход этой сессии — прямой запрос пользователя (перевод): «можешь переставлять
здания, чтобы они были в нормальном порядке» + «убери этот конвеер который на высоте находится,
и желательно перенести все заводы в отдельную зону как я и говорил, туда же транспорт, склады
возможно и тд» + отдельно «нужно дозировано подходить» к плотности перекрёстков (жалоба на
реальный 5-way узел на 3 здания). Полная методология, числа, найденный по ходу работы новый
баг и его фикс — `ROADS_V116_NOTES.md`, раздел «Проход 2026-09-26 — седьмой заход». Здесь —
краткая сводка.

**1. Перенос кластера.** Производственный комплекс (лесопилка+офис, мельница, бетонный завод,
металлобаза) + весь связанный с ним депо/автопарк (сервис-граф, стоянка, гараж) сдвинут по X на
`INDUSTRIAL_ZONE_OFFSET_X=-32` (новая константа, `Z` не менялся) — минимальный сдвиг, дающий
гарантированный зазор `≥13.2` юнита от любой из 10 позиций жилой спирали при любом `stageIndex`
(было `7.92`, полный перебор по всему кластеру и всем 10 позициям, не только по 4 зданиям).
Архетип «Склад» (`STAGES`, `archetype:'warehouse'`) сознательно НЕ перенесён — это обычная
позиция в общей стадийной спирали игрока, а не отдельное здание с фиксированными координатами;
вырывать его из общей прогрессии ради чисто косметического, явно помеченного пользователем как
«возможно» (низкая уверенность) запроса означало бы больший геймплейный риск, чем эстетическая
польза — задокументированный компромисс, ровно тот случай, который задание разрешило.

**2. Найденный вживую по ходу работы новый баг.** Чистая трансляция координат (без изменения
формы графа) была проверена реальным OBB-тестом и **нашла новую проблему**: въезд `junction`
привязан к неподвижной мастер-сетке, а весь кластер уехал вслед за собой — бывший короткий
(`4.2` юнита) въездной дек вырос до `27.8` юнита и на этой длине прошёл впритык
(`0.6` юнита) мимо `GENERATOR_POS`/конвейера, задев оба реальным пересечением (`3` штуки).
Фикс — не просто перенос, а реролит входа: кластер раньше стоял ЗАПАДНЕЕ въезда своим ЗАПАДНЫМ
краем (значит, естественно, входили с запада), а после переноса оказался ЦЕЛИКОМ западнее
въезда — входить нужно с его ВОСТОЧНОГО края. Новый узел `clusterGate` (пустой прямой отрезок
до кластера, затем один 90°-излом вниз к прежнему восточному листу дерева) + разворот
направления всей остальной цепочки (те же рёбра, тот же результат, просто пройдены с другого
конца). После фикса — **`0`** пересечений.

**3. Конвейер сквозь дорогу — окончательно устранено, мост убран.** Тот же реролит (депо-дороги
к бетону/металлу теперь пускаются через уже существующий с прошлого захода объезд
`depotDetourE`/`depotDetourS`, восточнее ОБОИХ зданий по X) впервые по-настоящему убирает
топологическую причину пересечения ленты и дороги (не просто переносит её — раньше спуск к
бетону/металлу стартовал МЕЖДУ концами ленты, что пересекало бы её при любом переносе кластера
целиком). Измерено реальным OBB-тестом: **`0`** пересечений. Раз мост больше не нужен ни при
одной проверенной геометрии — убран целиком (`CONVEYOR_BRIDGE_*`, `conveyorElevationAt()`,
`addConveyorSpanBox()`, раскосы опор из `1d57116`); лента и опоры вернулись к простой плоской
версии, какой были до `517fee7`/`1d57116`.

**4. Перекрёстки «дозированы».** Живое измерение ДО этого захода подтвердило жалобу: узел
`sawmillBypass` был реальным **4-way** (плюс один из его 4 деков полностью дублировал уже
нарисованный въездной дек — тот же `Box3` по одной оси, строгое X-подмножество). Реролит из
пункта 2 чинит это как побочный эффект без отдельной правки: `sawmillBypass` стал плоским
**2-way** проходом. Во всём живом графе кластера теперь ровно ОДИН настоящий перекрёсток —
`garageMid`, честный **3-way** (индустриальный коридор + автопарк + лесопилка), всё
остальное — простой сквозной проезд.

Тестирование: 10 перезагрузок — 0 новых ошибок; старый сейв грузится (позиция кластера
подтверждена и на старом сейве); разметка не пересобирается на холостом повторном вызове;
несвязанный апгрейд гаража не трогает stage-дороги; холостой простой — `0` удалённых дорожных
мешей на 5 тиках подряд; зазор подъезд↔здание — `0`; маршрут доставки источник→стройка —
полностью заасфальтирован на ближней (индекс 3) и дальней (индекс 7) стройках; стоянка автопарка
— `0` пересечений с дорогой; все живые аудиты (`v67`, `v76`, `stageRoads`) — все проверки
`true`. Два предсуществующих ложных `v114`-чека (`parkingProtectedFromRoads`,
`plankLoadingMatchesRoadNode`) остаются `false` — подтверждено сравнением с исходным файлом ДО
этого захода: тот же самый `false` там же, баг самого аудита (не относящийся к переносу), не
трогался, задокументирован честно.

## 2026-09-26 (шестой заход) — Индустриальный кластер: силос/миксер/лесопилка выглядели «плоско»

Пользователь прислал скриншот индустриального кластера (лесопилка/бетонный завод/конвейер) после
фикса раскосов конвейера (1d57116) с отзывом: «Всё прекрасно, но переделай пожалуйста этот завод и
конвеер, сделай красивее и лучше» — чисто художественный запрос, геометрия к этому моменту уже
корректна (см. changelog ниже), но читается утилитарно: плоский серый силос-цилиндр, безликий
валик миксера, коробки без отделки.

**Важное уточнение объёма работ, полученное в середине захода.** Пока эта работа шла, пользователь
отдельно попросил убрать сам приподнятый мост конвейера («убери этот конвеер который на высоте
находится») — отдельный, более крупный заход намерен перенести всю индустриальную зону (лесопилка,
бетонный завод, металлический склад, автопарк, склады) в отдельную зону вдали от жилой застройки, и
после переноса нужда в мосте через ту самую дорогу скорее всего отпадёт (мост со всеми опорами и
раскосами из 1d57116, вероятно, будет заменён обычным наземным конвейером на новом месте). Поэтому
этот заход **сознательно не трогает геометрию моста/раскосов/рамп конвейера** (ленты, `beltMaterial*`,
`addConveyorSpanBox`, `addConveyorSupport` — всё как было после 1d57116) — риск, что работа над этой
геометрией будет выброшена ближайшим же следующим заходом, признан не стоящим вложенных усилий.
Весь художественный полишинг в этом заходе ограничен зданиями/оборудованием, которые переживут
перенос независимо от итоговой высоты и положения конвейера: `buildConcretePlant()` (силос,
миксер) и здания в `buildSawmillScenery()` (офис/склад лесника, здание лесопилки) — сам конвейер
(ленты/опоры/раскосы моста, `tycoon-v116.html:3051-3159` в текущей нумерации, внутри той же
функции) не менялся ни на строку.

### 1. Бетонный завод (`buildConcretePlant()`, `tycoon-v116.html:3178-3378` после правки)

Было: один плоский `CylinderGeometry` силоса + `ConeGeometry` крышка одним и тем же серым
металлическим материалом, 4 голых стойки-подпорки без связи между собой, и барабан миксера,
целиком залитый одним бетонным оттенком (`createConcreteMaterial(0xc9c3b6)`) — визуально читался
как «труба» и «валик», как и описал пользователь.

Изменения (тот же единственный владелец функции, без нового патч-слоя):
- Силос: тело переведено на `createCorrugatedMaterial` (гофрированная сталь, переиспользует
  встроенную текстуру `assets_v31/metal.jpg` через существующий `getCorrugatedTexture`) вместо
  плоского металла; добавлены 2 воротника-коллара другого оттенка на стыке тело/крышка, крышка
  перекрашена в контрастный ржаво-рыжий металл (`0xa8532f`), сверху — маленький красный
  проблесковый маячок (эмиссивная сфера).
- Кольцо предупреждающих жёлтых полос у основания силоса (12 боксов по окружности) — переиспользует
  существующий по всему файлу приём «однотонные жёлтые повёрнутые боксы» (см. ветку
  `type === 'warehouse' || type === 'factory'` в архетипных деталях, `tycoon-v116.html:6128`),
  вынесенный в переиспользуемую `addHazardChevrons()` (`tycoon-v116.html:4807-4817`) для прямых
  участков и отдельным инлайн-циклом для кольца (кольцу нужен свой угол на каждый штрих,
  `addHazardChevrons` рассчитана на прямую).
- Служебная лестница (2 рейки + 8 перекладин) с двумя предохранительными полукольцами
  (`TorusGeometry`, `Math.PI` arc) и небольшая смотровая площадка с перилами у верха — тот же
  приём рейка+перекладина, что уже использовался для другой лестницы в файле.
- 4 опоры силоса теперь связаны горизонтальной рамой (4 бокса) у верха стоек вместо 4 независимых
  «голых кольев».
- Миксер: барабан перекрашен в металлик цвета строительной техники (`0xd9a520`) вместо единого
  бетонного оттенка, добавлены два кольца-обода (`TorusGeometry`) на концах барабана как дети
  самого `drum`-меша (наследуют его `rotation.z`, поэтому корректно охватывают его без ручного
  пересчёта базиса); у приводного (широкого) конца добавлен видимый редуктор-коробка + шкив —
  раньше барабан крутился без единой видимой причины; добавлены 4 опорные ножки под основанием,
  жёлто-чёрная предупреждающая полоса на переднем крае основания (`addHazardChevrons`) и щиток
  управления с двумя индикаторными лампочками (зелёная/красная, эмиссивные сферы).
- Труба подачи (`addPipeSpan()`, новый переиспользуемый хелпер рядом с другими `add*`-хелперами,
  `tycoon-v116.html:4790-4802` — по той же схеме «вычислить длину + сориентировать через
  quaternion», что уже применяется для секций ленты конвейера, `addConveyorSpanBox`, но без
  профиля высоты, который там нужен только самой ленте) визуально соединяет выход силоса со входом
  миксера — раньше два агрегата стояли рядом без всякой связи.
- Небольшая операторская будка (кремовый сайдинг `createSidingMaterial(0xefe6d6)`, красная крыша
  `createRoofMaterial(0xb3352a)` через `createGableRoof`, одно окно с синей вставкой через уже
  существующий `addFramedWindow()`, коричневая деревянная окантовка двери) — третье
  материальное/кровельное семейство на участке завода вместо «два станка + вывеска»; та же палитра
  (кремовый сайдинг + красная крыша + синее окно + коричневая окантовка), которую пользователь сам

Предполагалось, что матовое стекло HUD-панелей постоянно пересэмплирует движущийся фон (машины,

spikesOver2 8→9** — отключение блюра не снизило churn (в пределах шума). Гипотеза отклонена.

**Настоящая причина — два независимых, наслоенных друг на друга слоя «feedback»-анимации статов,
оба реагирующие на одни и те же значения (`money`/`planks`/`concrete`/`metal`/`population`),

  идёт пассивный доход. Но CSS-переопределение того же прохода v48 (`#hud

  `!important` — выигрывает каскад безусловно) **полностью отключало саму анимацию**. То есть JS
  весь этот цикл прогонял вхолостую: ноль визуального эффекта, реальный принудительный reflow
  каждый раз. Комментарий рядом в коде прямо это документировал («v48 replaces it»), но сам
  JV47-код так и не был удалён.
- **V48 (`installMeaningfulHUDFeedback`/`pulseStat`, ~`tycoon-v116.html:26224-26256`).**

  порог сразу же, как истекает кулдаун — то есть «осмысленная, ограниченная по частоте» отдача на

### 1. «Дорога перекладывается после каждого апгрейда» — реальный источник: разметка, не асфальт

Место: `apply()` в `v94-road-marking-cleanup` (`tycoon-v116.html:32106`, до фикса). Функция на
каждый вызов делала `hideLegacy`+`normalizeAsphalt`+`rebuildRoadUnion` (у него уже был свой
`lastUnionSignature`-кэш, поэтому асфальт не пересобирался) и затем **безусловно** для каждого
корня `addDashes(root)` → `removeLayer(root)` (снос группы `v95UnifiedMarkings` с dispose
геометрии/материалов) → пересоздание всех дэшей заново. Никакой проверки «а изменилось ли
что-то» не было — единственный владелец разметки полностью пересоздавал её на каждый вызов.

`apply()` вызывается из `syncAll()` (`v113`, `tycoon-v116.html:33937` до фикса) на **каждом**
`refreshInfrastructureWorldV37()`, а он, в свою очередь, срабатывает при завершении таймера
любого апгрейда дороги/освещения района (`tycoon-v116.html:10191`/`10179`) — то есть на каждый
клик «Улучшить дорогу»/«Улучшить освещение» вся белая разметка по всей карте демонтировалась и
рисовалась заново. Визуально это неотличимо от «дорогу перекладывают».

**Тест до фикса** (`scratchpad/roads116/diag1.js`, снимок мешей с тегами
`v59RoadDeck/v86StageRoad/v66ServiceRoad/v116PersistentRoad/.../v95UnifiedDash` по `uuid` до/
после реального клика): апгрейд дороги района (клик `[data-district-roads="suburb"]`) —
**37 уничтожено / 37 создано** (полный набор дэшей); апгрейд освещения другого района — 37/37;
`upgradeCityDistrict('waterfront')` (тот же код, что за кнопкой) — 37/37; и даже **полностью
не связанный апгрейд гаража автопарка** (`buyBaseUpgrade('garage')`) — тоже 37/37. Изолированный
холостой прогон без единого действия (`diag_idle.js`, 6 тиков по 1.5с) — 0/0, то есть проблема
не в фоновом таймере, а именно в том, что любое из этих действий доходит до `apply()`.

Фикс (`tycoon-v116.html:32106`, тот же единственный владелец, без нового патч-слоя): добавлена
`applyInputSignature()` — тот же приём, что уже используют `serviceGraphSignature()`/
`drivewaySig()` в этом файле (сигнатура по `uuid`+`visible` реальных дорожных мешей + условие
покрытия дорог по районам), и `apply()` возвращает закэшированный результат, если сигнатура не
изменилась. Реальное изменение сети (новый мост, новый уровень дороги, новый штрих) меняет
набор `uuid` или условие → полный пересчёт по-прежнему происходит; повторный вызов с тем же
состоянием — нет.

**Тест после фикса** (тот же `diag1.js`): апгрейд дороги района — **0/0** (86 сохранено);
апгрейд освещения — 0/0; `upgradeCityDistrict` (район реально поднялся с L2 на L3, разметка не
пересобиралась, но легитимно **добавились** 34 новых меша — бордюр/тротуар/переход L3,

ничего не изменилось, и по-прежнему честно достраивается там, где что-то реально появилось.

### 2. «Дорога пересекает парковку» — реальный источник: парковку сдвигает чужая система очистки меток

Место: `run()` в `v102-label-and-road-clearance` (`tycoon-v116.html:32538`, до фикса). Проход
предназначен для мелких UI-подсказок («автопарк», «команда», «город» — плашки-кружки над
кнопками мира) — он ищет группы, чей текст похож на подпись, и через `nudgeGroup()` сдвигает их
подальше от дороги. Ловушка: критерий матчинга был `(labelText || '') + ' ' + (obj.name || '')`,
а НЕ только текст подписи. Реальная группа автопарка (`v116FleetYard`, вся стоянка со всеми
боксами/линиями разметки — `tycoon-v116.html:28537`, слой `v65-depot-traffic-queue-fix`) так и
называется — регэксп `/Fleet/i` ловил её саму, целиком, как будто это маленькая UI-плашка.

`nudgeGroup()` читает `group.getWorldPosition()` — то есть позицию САМОЙ группы (у
`v116FleetYard` она равна `(0,0,0)`, потому что все дочерние меши несут собственные абсолютные
локальные координаты вроде `(-8.70, ..., 6.72)`, а сама группа-контейнер не смещена). `(0,0,0)`
физически лежит на центральной магистрали (`masterRoadSegmentsV362`, ось X=0). Функция честно
нашла «UI-плашку в 0 юнитах от дороги» и оттолкнула её на `1.34` — но оттолкнула **всю стоянку
целиком**, а не что-то маленькое. Проход перезапускается после каждого `stageApi.refresh()`
(3 раза, `+80/+420/+1100мс`) плюс стартовые прогоны — за несколько последовательных пересборок
смещение накопилось.

**Тест до фикса** (`scratchpad/roads116/diag_fleet.js`): `scene.getObjectByName('v116FleetYard').
position` = `(4.02, 0, 0)` (должно быть `(0,0,0)`); плита стоянки (меш `lot`,
`BoxGeometry(11.92,...,3.72)`, автор задумывал центр `x=-8.70`) реально стояла в мире с
`Box3 = {min:[-10.64,...], max:[1.28,...]}` — то есть кабинет стоянки заехал почти до `x=1.28`.
Реальное пересечение `Box3.intersectsBox()` с сегментом магистрали `arterial-master`
(`x∈[-1.24,1.24]`) — **1 пересечение** (не самоотчёт файла, а честный тест бокс-в-бокс на
фактических мировых координатах после `updateWorldMatrix`).

Фикс (`tycoon-v116.html:32538`, тот же владелец, без нового слоя): критерий сузили до **только**
`labelText` (реальный текст подписи, не внутреннее имя объекта) и добавили явное исключение
известных инфраструктурных корней (`v116FleetYard`, `cityWorldRuntime.stageRoads/masterRoads/
transportAccessRoads`) — они никогда не должны рассматриваться как «маленькая UI-плашка».
Дополнительно в `rebuildParkingV65()` (`tycoon-v116.html:28537`) явное
`g.position.set(0,0,0)` с комментарием — защита от повторения той же ошибки другим будущим
патчем, который случайно заматчит имя.

**Тест после фикса**: `v116FleetYard.position` = `(0,0,0)`; плита стоянки —
`Box3 = {min:[-14.66,4.86,...], max:[-2.74,8.58,...]}`, полностью в стороне от `x∈[-1.24,1.24]`
магистрали; **0 пересечений** `Box3.intersectsBox()` по всем реальным дорожным мешам
(`v59RoadDeck`/`v86StageRoad`/`v66ServiceRoad`/`v116PersistentRoad`). Скриншот
(`scratchpad/roads116/after_fleetyard_topdown.png`, вид сверху) визуально подтверждает: серая
стоянка с разметкой боксов отделена травой от чёрной дороги, наезда нет.

### 3. «Отдельные подъезды к зданиям» — реальный источник: два независимых определения «края здания» разошлись на 1.7 юнита

Первый заход (см. предыдущую запись этого changelog и `ROADS_V116_NOTES.md`) измерил, но не
исправил: подъездные меши с ролью `stage-driveway` реально существуют и подключают здания к
сети, но типичный зазор от края застройки до дороги/подъезда был `~1.8-3.5` юнита вместо `~0`.
Этот заход находит и закрывает точную причину.

Место: `stageRoadEndpointV367()` (`tycoon-v116.html:15338`, до фикса). Эта функция — ЕДИНАЯ
точка, в которой физически заканчивается асфальт последнего сегмента дороги для stage-здания:
её использует и канонический маршрутизатор `plan()` в `v86-canonical-stage-roads`
(`tycoon-v116.html:31356`, `finalEnd=stageRoadEndpointV367(i)`, попадает в путь на
`tycoon-v116.html:31393`), и bootstrap-фоллбэк `stageRoadPolylineV367`
(`tycoon-v116.html:15361`) — то есть какая бы из двух систем ни оказалась «живой» на момент
рендера, обе кладут асфальт ровно до этой точки. Она же задаёт позицию декоративного pull-in
bay (`stageDrivewayGeometryV351.bay`, `tycoon-v116.html:13679`, использует
`stageRoadEndpointV367` напрямую) и точку, куда едут служебные машины
(`worksiteVehicleApproach`, `tycoon-v116.html:13684`).

До фикса `stageRoadEndpointV367` откладывала от здания `радиус_коллизии + 1.82` юнита. Проблема
в том, что в этом же файле, в той же самой функции-соседке (`stageDrivewayGeometryV351.edge`,
`tycoon-v116.html:13678`), уже посчитан «настоящий край» здания — `радиус_коллизии + .12`. Это
разные конкретные точки на карте, отличающиеся ровно на `1.82-.12=1.70` юнита: одна («true
edge») используется для аудита/логистики, другая («road endpoint») — для того, где физически
кончается асфальт. Комментарий на месте старого кода объяснял `+1.82` желанием «оттащить рот
подъезда подальше, чтобы дорога не заезжала визуально в дома» — но это рассуждение появилось
до того, как `stageAccessRadiusV92()` стал брать радиус из `buildingCollisionRadius()` (реальный
архетип здания, `stage.baseSize*.64+...`), то есть до того, как радиус вообще стал точным. Раз
радиус уже равен настоящему футпринту, добавочные 1.7 юнита сверху — это просто трава, которую
асфальт больше не покрывает, а комментарий `v35.3` в `refreshDrivewaysAndApronsV353`
(`tycoon-v116.html:13976`) прямым текстом запрещает рисовать здесь второй, дублирующий слой
асфальта («V86 is the only owner of the stage driveway asphalt») — то есть ничего другого этот
разрыв заполнить и не могло.

**Тест до фикса** (`scratchpad/roads116/diag_driveway2.js`; здания через
`spawnBuilding(index,1,{grow:false})` по проектной конвенции; зазор считается от НАСТОЯЩЕГО
