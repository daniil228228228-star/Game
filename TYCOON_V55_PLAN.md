# Tycoon v55 — план разработки

Продолжение линии v36 (`TYCOON_V36_PLAN.md`/`CHANGELOG_V36.md`) — пользователь загрузил
файл на много итераций дальше того, что было сделано в этой сессии («v55 — Stability
Corrective», ~28000 строк исходно). Подтверждено grep'ом: файл содержит всю работу
v36-линии этой сессии (сетка дорог без диагоналей, кнопки фонарей/дорог района, детсад
и т.д.) — но НЕ содержит правку зависающего грузовика (`_playerEscapeTimer`), сделанную
в этой сессии буквально перед получением этого файла, что подтверждает: пользователь
вёл параллельную внешнюю разработку поверх более раннего снимка (вероятно, присланного
standalone-файла v36), не связанную с этой конкретной последней правкой.

Файл игры: `tycoon-v55.html` (~26920 строк после вырезки вендоров/ассетов).
Переиспользует `vendor_v31/three_r128/` и `assets_v31/` (текстуры побайтово идентичны,
подтверждено sha256) — новых ассетов не добавлено.

## Текущий запрос пользователя (2026-09-22)

Дословно: «проводи аудит на баги и адекватность, это новый файл».

## Структурное отличие от v36 — важно для дальнейшей работы

В отличие от v36 (4 крупных блока `<script>`), v55 состоит из **16 отдельных блоков
`<script>`**, наслоённых поверх основного игрового кода (строки 18400+) — файл
многократно патчился внешне отдельными добавляемыми скриптами, а не редактированием на
месте. Это тот же паттерн переприсваивания функций (`fn=function(){...}`), что уже
встречался внутри самого v36 (`v36.2→v36.5→v36.6→v36.7`), но теперь ещё и на уровне
внешней структуры HTML. **Важное следствие для любой будущей правки этой линии**: перед
изменением любой функции нужно грепать ВСЕ её определения по всему файлу и работать
именно с последним (реально исполняемым) — этот урок уже не раз подтверждался в этой
сессии, но в v55 он особенно критичен из-за количества слоёв патчей.

## Критическая находка при импорте — требует расследования, не решена

У файла есть собственная система самодиагностики стабильности:
`V54_STABILITY`/`activateStabilityModeV54()`/`emergencyLoopV54()` — watchdog,
который следит, не завис ли основной игровой цикл (`lastCoreFrame`) дольше 1200мс, и
если да — включает аварийный fallback-рендер (упрощённое движение/рендер) с видимой
плашкой «STABILITY» в углу экрана. Само название файла («Stability Corrective»)
напрямую про эту систему.

При headless-проверке этой сессии (Playwright, `--use-gl=swiftshader`, тот же метод,
что использовался для всех предыдущих версий без проблем) страница реально
**залогировала `[v54] stability mode: core heartbeat stalled`** при загрузке, после чего
`page.screenshot()`/`page.evaluate()` зависали намного дольше обычных таймаутов (60+
секунд). Не установлено, является ли это:
(a) настоящей регрессией/багом в свежих патчах v55 (основной цикл действительно виснет
    даже в реальном браузере), или
(b) артефактом того, что эта песочница использует программный (не аппаратный)
    рендеринг WebGL, а сцена v55 стала значительно тяжелее v36 — то есть на реальном
    устройстве с GPU-ускорением этого может не быть.

Есть подсказка в консоли: `GL Driver Message ... GPU stall due to ReadPixels` — говорит
скорее в пользу (b), но это не доказательство, и сама система `V54_STABILITY` явно была
добавлена ПОТОМУ ЧТО кто-то (предыдущий внешний проход разработки) уже сталкивался с
реальными зависаниями основного цикла в каких-то условиях — иначе зачем вообще писать
watchdog. Это первый и главный пункт полного аудита.

## Результаты полного аудита (2026-09-22)

### 1. Вопрос стабильности/основного цикла — РЕШЁН: артефакт песочницы, не баг

Проверено эмпирически через Playwright с щедрыми таймаутами (до 220+ секунд ожидания,
poll вместо блокирующего `page.screenshot()`), три конфигурации, сервер — `python3 -m
http.server` из корня репозитория:

- **Desktop viewport, дефолтные флаги** (`--use-gl=swiftshader --enable-webgl
  --ignore-gpu-blocklist`, `VISUAL_MOBILE=false` → рендерер использует
  `antialias:true` + `PCFSoftShadowMap` 2048×2048, `V54_IOS_STABILITY=false`): `[v54]
  stability mode: core heartbeat stalled` реально логируется через ~2.7с после начала
  загрузки, счётчик `V54_STABILITY.frame` замирает на 6 и **не восстанавливается вообще**
  — 17 последовательных `page.evaluate()` с individual-таймаутом 10с все проваливаются,
  суммарно >190с без единого успешного round-trip; `renderer.info`/`page.screenshot()` с
  запасом 15-30с тоже проваливаются. В консоли — `GL Driver Message ... GPU stall due to
  ReadPixels` через 1-2.5с после старта.
- **То же самое, но с `--use-gl=angle --use-angle=swiftshader
  --enable-unsafe-swiftshader`** (флаг, который сам Chromium рекомендует в своём
  предупреждении «Automatic fallback to software WebGL has been deprecated») — идентичная
  картина: зависание на кадре 4, `evaluate()` не проходит вплоть до 107+ секунд ожидания.
  Значит дело не в «устаревшем» пути свифтшейдера конкретно, а в стоимости самих
  desktop-настроек рендера под ЛЮБЫМ программным растеризатором.
- **iPhone 13 эмуляция** (touch pointer + iOS UA → `VISUAL_MOBILE=true` И
  `V54_IOS_STABILITY=true`, что по строкам 1693/1700-1701 отключает `antialias` и весь
  `shadowMap` целиком) — тот же файл, тот же сервер, тот же программный WebGL-бэкенд:
  загрузка чистая, счётчик кадров растёт стабильно (7→11→15→…→58 кадров за ~7 секунд,
  ~9 fps), `V54_STABILITY.fallbackActive` ни разу не становится `true`, стабильное
  состояние достигнуто за ~11с, `page.screenshot()` проходит сразу.

Это точно изолирует переменную: зависает именно **desktop-уровень качества рендера
(реалтайм антиалиасинг + мягкие тени 2048×2048)** под программным растеризатором — не
логика `animate()`/игрового цикла. Мобильный уровень качества, который разработчики уже
сделали специально для слабых/тач-устройств, рендерится нормально на том же самом
программном бэкенде.

Статический разбор `animate()` (строка ~12296) и вызываемых из неё функций:
- **Ни одного бесконечного цикла.** Все 22 `while`-цикла в файле — с явным условием
  завершения (ограничены длиной массива, счётчиком с `guard++<N`, либо «выгребание»
  `children.length` с `.pop()`/`.shift()` внутри, что естественно завершается).
- **Ни одного явного `gl.readPixels`/`toDataURL`/`getImageData` в коде игры** — грепом по
  всему файлу совпадений нет. Предупреждение «GPU stall due to ReadPixels» — это
  внутренний compositor-readback самого Chromium/ANGLE под swiftshader, не вызов из кода
  игры.
- Сама `animate` действительно переопределяется один раз (`const _animateV35=animate;
  animate=function(){_animateV35();};`, около строки 12995) — чистая обёртка-делегат без
  побочных эффектов, не источник проблемы.

**Вывод: сценарий (b), не (a).** На реальном устройстве с аппаратным WebGL-ускорением
(подавляющее большинство телефонов и десктопных браузеров) это не воспроизведётся —
проблема специфична именно для принудительного программного рендеринга в этой песочнице
в сочетании с полным визуальным качеством desktop-режима. `V54_STABILITY` при этом
работает ПРАВИЛЬНО и как задумано (корректно триггерится, корректно переключается на
упрощённые движение+рендер) — это не повод считать её сломанной, а подтверждение, что
защитная сетка (для реальных краевых случаев — свёрнутая вкладка уже отдельно
обрабатывается через `document.hidden`, по-настоящему слабые устройства, тепловой
троттлинг) работает. Менять её не рекомендуется и не требуется — правки не вносились
(вне рамок задачи по прямому требованию пользователя).

Практическое следствие для пользователя: если в будущем понадобится безголовое
QA/скриншот-тестирование именно desktop-профиля этого файла, стоит либо запускать его в
браузере с реальным GPU (не headless-песочница), либо тестировать через мобильную/iOS
эмуляцию (`VISUAL_MOBILE`/`V54_IOS_STABILITY`), которая надёжно рендерится и на
программном бэкенде.

### 2. Конфликты патчей между 16 слоями `<script>`

Структура подтверждена: 15 тегов `<script>` (близко к оценке «16» из первичного импорта),
основной код (896-17254) + `v43` (17337-17537, кэш текстур зданий) + `v44-refined-script`
(17624-24500, крупнейший патч, ~6876 строк) + последовательно `v45`…`v53`
(24697-26912) — каждый в собственной IIFE с именованным объектом состояния
(`V46`…`V53`) и защитными `typeof x!=='undefined'` перед обращением к переменным более
ранних слоёв. Стиль последовательный, не производит впечатления наспех слепленного.

- **`addRoadNodeCapV353=function(){};`** (строка 14766) — пустышка, изначально
  найденная в этой же сессии как баг `v36.5` (см. `CHANGELOG_V36.md`, запись
  2026-09-21). Проверено по актуальному `tycoon-v36.html`: там **идентичная** строка на
  таком же месте (`addMasterGridJointCapsV368` как обходной путь для стыков магистральной
  сетки). Значит это НЕ новый баг v55 — это унаследованное, уже проанализированное и
  намеренно оставленное состояние из общей линии v36 (пропущены декоративные заглушки на
  части дорожных стыков, чисто косметически, не влияет на маршрутизацию/коллизии). Править
  не нужно.
- **Легаси-баг «зигзаг v34»** (толстая диагональная дорога хаб→stage0→…→stage9 поверх
  сетки, найденная и удалённая в v36.10, `CHANGELOG_V36.md` запись 2026-09-21 «Главная
  находка: старая дорога-зигзаг с v34 всё ещё была активна») — в v55 **уже отсутствует**:
  строки 1820-1837 содержат тот же самый объясняющий комментарий про удаление этих двух
  циклов отрисовки, что подтверждает — снапшот v55 сделан ПОСЛЕ этого фикса.
  Подтверждает свежесть снапшота относительно этой конкретной находки.
- **Зависающий грузовик** (см. «Критическая находка» выше в этом файле) — фикс от
  2026-09-22 (`moveWorkVehicle`, боковой манёвр при простое рядом с игроком) в v55
  отсутствует, как и было предположено при импорте. Баг минорный и самовосстанавливающийся
  (грузовик застревает только если игрок стоит неподвижно <1.15 юнита от маршрута у хаба;
  отпускает сразу при движении игрока) — не исправлялся: (а) не проходит по критерию
  «тривиально и однозначно безопасно» из инструкции задачи, (б) касается логики движения
  транспорта, что близко к явно исключённой из этой задачи зоне (fleet/логистика).
  Оставлено на усмотрение пользователя.
- **`suppressAutoSaveV36`** (фикс бага кнопки «Сброс прогресса» из аудита v36,
  2026-09-21) — присутствует (строка 938) и **корректно уважается всеми более поздними
  слоями**, включая сброс доп.-ключей `v40`/`v41`/`v42` (строки 16371, 16803, 17197) и
  систему координации сохранений/recovery-снепшотов `v52` (строки 26563, 26605, 26615,
  26624, 26726). Баг класса «no-op сброс» не воспроизводится в поздних слоях v55.

### 3. Анти-баг чек-лист (статическая проверка, не полный живой прогон — бюджет времени

## Функциональный аудит через живое UI-тестирование (2026-09-22, продолжение)

Новый запрос пользователя (дословно, перевод): «теперь проверяй уже саму функциональность
— где там поправить, где может даже не запускается». Это смена фокуса с предыдущего прохода
(статика/стабильность) на **живое тестирование**: реальные клики по DOM через Playwright
(`page.click()`/`dispatchEvent`, НЕ прямые вызовы игровых функций), с iPhone 13 эмуляцией
(тот же приём, что решил вопрос №1 выше). На этот раз правки вносились — с гораздо более
низким порогом «тривиально» по прямому требованию задачи.

### Найдено и исправлено

**1. КРИТИЧЕСКИЙ: основной цикл стройки был сломан на каждом до единого нажатии «Строить»**
(`decorateConstructionSiteV45`, было на строке ~24862, патч-слой v45). Пойман только живым
кликом — статический аудит (предыдущий проход) его пропустил, потому что исключение
глушится защитным `safeFrameCallV54`-врэппером и не всплывает как `pageerror`.

Живой тест: телепорт игрока к `currentPad`, реальный `page.click('#actionBtn')`. Результат
**до фикса**: `stageIndex` не меняется, `currentPad` не обнуляется, но `money` тратится
дважды за один клик (300→200 вместо 300→250), в консоли дважды
`[v54] updatePlayer failed TypeError: Cannot set properties of undefined (setting 'v45Site')`.

Корень: `spawnConstructionSite()` (строка ~5281, код ДО патч-слоёв) возвращает не
`THREE.Object3D`, а обычный дескриптор `{group, jibPivot, hook, ..., buildRef:null}` — сам
3D-узел лежит в `site.group`. Патч v45 (`decorateConstructionSiteV45`) обращался к
`site.userData`/`site.add(...)` напрямую на этом дескрипторе, что бросало
`TypeError` при КАЖДОМ вызове. Поскольку `spawnConstructionSite()` вызывается из
`spawnBuilding()` уже ПОСЛЕ `growingMeshes.push(build)`, но ДО `scene.add(mesh)` и
`buildings.push(entry)`, необработанное исключение рвало цепочку насквозь:
`purchaseCurrentPad()` прерывался до `stageIndex=index+1`, до `currentPad=null`, до
`spawnPad()` следующей стройки, до `save()` — а `interactRequested` (сбрасывается только
ПОСЛЕ успешной покупки) оставался `true`, так что на следующем же кадре тот же клик
проигрывался заново, вновь списывая деньги, пока не кончался слот стройки
(`constructionSlotAvailable()`) или деньги. Игрок видел: площадка исчезает, деньги тают,
здание не появляется никогда.

Фикс: `decorateConstructionSiteV45` и `updateConstructionSitesV45` теперь работают с
`site.group` вместо `site`. Затронуты все вызовы `spawnConstructionSite` — основной цикл
строек, апгрейды, жильё/поликлиника/полиция/школа/детсад/коммерция/парк/пожарная,
спецпроекты (`startSpecialProject`).

Живой тест **после фикса**: `page.click('#actionBtn')` → `stageIndex` 0→1 за один клик,
`money` 300→250 (одно списание), `growingMeshes.length`=1 (не 2), `buildings.length`=1,
0 ошибок консоли. Через 8с реального ожидания: `growingMeshes.length`=0, здание
`visible:true`, `underConstruction:false` — полный цикл строительства подтверждён живым
кликом от начала до завершения. Регрессия проверена также для спецпроектов
(`data-project="park"` → `specialProjectRuntime.site.group` существует, 0 ошибок).

**2. Кнопка «Купить участок» была нерабочей (с вводящим в заблуждение текстом) в любом ещё
не развитом районе** (`postProcessCityPanelV38`, было на строке ~15641, патч-слой v38).
`infrastructureReadyV38(id)` = `need>0 && road>=need && light>=need`; на уровне района 0
`need=0`, поэтому `ready=false` — хотя реально ничего не требуется. Это блокировало ВСЕ
кнопки карточки района, кроме `data-district`/`data-v38-road`/`data-v38-light`, включая
`data-land-buy`, с бессмысленной подсказкой «Roads and lighting L0 required» (нужен
уровень L0, что тривиально уже выполнено).

Важно: реальная бизнес-логика (`buyLandPlot`, обёрнута в `requireInfrastructureV38` на
строке ~15534) и так корректно и отдельно проверяет то же самое, с человеческим текстом
«Open the district first» — то есть даже без UI-фикса игрок не смог бы купить участок
преждевременно, но получал вместо чёткого сообщения бесполезно заблокированную кнопку.
Проверено живым кликом: до фикса Playwright не может дождаться `enabled`-состояния кнопки
(таймаут); после фикса кнопка кликабельна, и клик корректно всплывает через реальную
бизнес-логику с тостом «Open the district first» и без списания денег — то есть фикс
только чинит UI-уровень, не трогает и не ослабляет реальный гейт. Подтверждено, что
все 11 действий района (`buildResidentialBlock`, `buildCivicBuilding`,
`buildPoliceStation`, `buildSchool`, `buildKindergarten`, `expandNeighborhood`,

## Закрытие последнего оставленного пункта: троттлинг пересборки Автопарк/База/Тендеры (2026-09-22)

Продолжение функционального аудита — закрывает последний оставшийся пункт из раздела

трогали это, считая правку «архитектурно широкой», поскольку эти функции переиспользуются
из множества других мест (прямые клики по кнопкам апгрейда/сервиса/приоритета/тендера).

### Найденное точное место вызова

Грепом всех определений `updateHUD` (16 слоёв патчей переопределяют её, каждый раз через
`const _old=updateHUD; updateHUD=function(){_old(); ...};` — то есть каждый следующий слой
ОБОРАЧИВАЕТ предыдущий, а не заменяет целиком) подтверждено: единственное место, где
`updateHUD` вызывает `renderFleetPanel`/`renderBasePanel`/`renderTendersPanel`, — это слой
`v30.1` (строка 8578-8586, `const _updateHUDV301=updateHUD; updateHUD=function(){...}`).
Все более поздние слои (`v35` 12963, `v35.1` 13105, `v36` 13806, `v36.1` 14141, `v47` 25451,
`v48` 25632, `v50` 26205, `v52` 26739) вызывают `old.apply(this,arguments)`/`_oldVXX()`
внутри своей обёртки — цепочка вызовов всегда доходит до тела `v30.1`, поэтому фикс именно
там гарантированно исполняется на каждом реальном вызове `updateHUD()`, независимо от того,
сколько более поздних слоёв её обернуло.

Сам тик подтверждён на строках 12395-12402: `goalHudAccumulator += dt; if
(goalHudAccumulator >= (VISUAL_MOBILE ? 0.20 : 0.16)) { goalHudAccumulator = 0;
updateHUD(); }` — ровно 0.20с на мобильном профиле, как и задокументировано ранее.

### Фикс — локальный троттлинг на месте вызова (не внутри самих render-функций)

В теле `updateHUD` слоя `v30.1` (строка 8578) добавлен per-панельный таймстамп
`_panelRenderThrottleV55={fleet:0,base:0,tenders:0}` и константа
`PANEL_RENDER_THROTTLE_MS_V55=350` (мс). Каждый из трёх вызовов `render*Panel()` теперь
условен: `if(overlay.show && performance.now()-lastRenderedAt>=350){lastRenderedAt=now;
render*Panel();}`. `renderFleetPanel`/`renderBasePanel`/`renderTendersPanel` НЕ изменены —
фикс целиком на уровне вызывающего кода, риск для переиспользующих их мест нулевой.

**Прямые вызовы после реального действия игрока не троттлятся и не задеты**: подтверждено
грепом всех вызовов трёх функций — `buyFleetUpgrade` (8392), `buyBaseUpgrade` (8402),
`startMajorTender`/`checkMajorTenderProgress` (8514, 8533), обработчики `openFleetBtn`/
`openBaseBtn`/`openTendersBtn` (8557-8559, немедленный рендер до открытия панели),
`buyUniversalTruck` (8654), `serviceFleetKey` (8670, 8679) — все они вызывают
`render*Panel()` НАПРЯМУЮ, минуя `updateHUD()` и наш троттлинг-таймстамп, поэтому клик
по любой кнопке продолжает обновлять панель мгновенно на этом же кадре, как и раньше.
Троттлинг ограничивает только фоновый опрос из `updateHUD()`, который просто перерисовывал
тот же самый грид впустую, пока в нём ничего не менялось.

### Найдено и исправлено

**Задвоенная иконка в HUD-плашке денег** (`#moneyStat`, строка 692 разметки + строка
26014 CSS). Патч-слой `v36` (`ensureHudIconV36('moneyStat','cash')`, строка 13711)
добавляет SVG-иконку «cash» (скруглённый прямоугольник со значком купюры) первым
дочерним элементом внутрь `#moneyStat` — но отдельная, независимая система того же
слоя (`installIconObserversV36`/`iconizeTextNodeV36`, MutationObserver, следит за
текстовыми узлами и автоматически подменяет символ 💰 внутри `<span class="icon">` на
ТУ ЖЕ САМУЮ SVG-иконку «cash»). Обе системы не знают друг о друге, поэтому в живом DOM
рядом оказывались два идентичных значка. Для остальных денежных/ресурсных плашек
(`progress`, `planks`, `concreteAmt`, `metalAmt`, `populationAmt`, `carriedLogs`) слой
`v36` предусмотрел парный `stripHudEmojiV36()` (строка 13717) — regex, вычищающий
исходный эмодзи-символ из `textContent`, — но для `moneyStat` эта чистка не была
предусмotrena, потому что эмодзи там сидел не в текстовом узле напрямую, а в отдельном
`<span class="icon">💰</span>`, который не входит в карту regex'ов `stripHudEmojiV36`.
Итог: единственная HUD-плашка из шести, где задвоение реально происходило и оставалось
насовсем (не разовый глюк рендера, а стабильное состояние DOM на каждой загрузке).

Подтверждено прямым чтением DOM (`page.$eval('#moneyStat', el=>el.outerHTML)`) до и
после: до фикса — `<span class="ui-stat-icon"><svg>...cash...</svg></span><span
class="icon"><span class="ui-inline-icon"><svg>...тот же cash...</svg></span></span>`
(два SVG), после фикса — один `<span class="ui-stat-icon">`. Визуально на скриншоте это
были два одинаковых значка «купюра с кружком» впритык друг к другу перед числом «300» —
при беглом взгляде читается как единая замусоренная иконка, а не как осмысленный
повтор, и не похоже на два разных, специально задуманных значка.

Фикс — минимальный, два места, только разметка/CSS, без единой строки JS-логики:
1. Строка 692: убран статический `<span class="icon">💰</span>` из HTML-разметки
   `#moneyStat` (сама SVG-иконка «cash» по-прежнему приходит рантаймом через уже
   существующий `ensureHudIconV36`, как и у остальных пяти плашек — паттерн просто
   приведён к тому же виду, что и у них).
2. Строка 26014: селектор золотого `drop-shadow`-свечения иконки денег переключён с
   `#moneyStat .icon` (класс, которого после правки №1 больше нет) на
   `#moneyStat .ui-stat-icon` (реальный элемент SVG-иконки) — чтобы декоративное
   свечение не потерялось молча.

Живая проверка (Playwright, iPhone 13 эмуляция): чтение `outerHTML` до/после подтвердило
ровно один `<span class="ui-stat-icon">` в `#moneyStat`; смок-тест — `money +=
12345; updateHUD();` — число в HUD корректно обновилось на «12.6K», иконка осталась
одна, свечение на месте (не потеряно); 0 ошибок консоли на всём прогоне (загрузка +
чтение DOM + смок-тест). Дополнительно грепом/DOM-инспекцией проверены все остальные
пять денежно-ресурсных плашек (`progress`, `planks`, `concreteStat`, `metalStat`,
`populationStat`, `carriedLogs`) — задвоения нигде больше нет, у каждой ровно один
`<span class="ui-stat-icon">`, других мест той же категории бага не найдено.
`saveVersion` не менялся (55) — фикс чисто визуальный, не сериализуется.

Общее визуальное впечатление от мира на мобильном профиле рендера (`VISUAL_MOBILE`,
без сглаживания и мягких теней) — чистое, стилизованно-минималистичное («low-poly»)

техника — без объектов, которые бы читались как «случайно огромные» или «случайно
крошечные»).

**Не баг, задокументировано для контекста**: при скриптованной телепортации камеры
(быстрые последовательные `page.evaluate`, переставляющие `player.position`/
`camera.position` каждые ~0.7с для серии скриншотов) наблюдаемый тестовый метод сам
временно триггерил уже задокументированный `V54_STABILITY`-watchdog («⚙️ Stability mode
enabled») — это ожидаемая реакция существующей защитной сетки на синтетические,
неигровые скачки состояния от самого тест-скрипта (не связано с обычным перемещением
игрока через джойстик), полностью согласуется с выводом первого прохода этой сессии
(«V54_STABILITY» — не баг, а корректно работающий watchdog). На чистой загрузке без
скриптованных телепортов (замер `check_stability.mjs`, 14с наблюдения) `fallbackActive`
ни разу не становится `true`. Не является находкой дизайн-аудита, упомянуто только
чтобы объяснить плашку «Stability mode enabled», видимую на части приложенных
скриншотов серии `10_hub_*`/`2x_*district*`.

### UI/HUD/панели: визуальный обзор — главная находка (не исправлено, требует решения пользователя)

**Непоследовательная локализация — самая заметная и самая распространённая проблема
дизайна во всём UI.** На одном и том же экране вперемешку встречаются русский и
английский текст, при этом язык интерфейса выставлен на «RU» (кнопка `langBtn`
показывает «RU» как цель переключения, то есть текущий показанный язык должен быть
английским по логике переключателя — но фактически показывается смесь, а не чистый EN).
Примеры, зафиксированные скриншотами:
- Меню «☰» (`systemsOverlay`, «Company»): заголовки секций на английском
  («COMPANY PROGRESSION», «SETTINGS», «YANDEX GAMES READY»), подпись прогресса на
  английском («Small Contractor», «Next: Local Contractor»), но подписи строк меню —
  на русском («Мета-прогрессия», «Команда», «Спецпроекты»), а настройки — тоже на
  русском («Звуки», «Музыка», «Вибрация», описания под ними).
- Панель «Bonuses»: заголовки карточек на русском («x2 доход», «Быстрая стройка»,
  «Пакет снабжения»), но их описания и кнопки — на английском («Doubles all income for
  3 minutes.», «Ready», «Claim», «Instant»).
- Панель «Achievements» — полностью на английском, без примеси русского.
- Панель «City & Development» — почти полностью на английском («Company Reputation»,
  «Housing demand», «Municipal Bid Board», «Road Rehabilitation Program»), кроме
  надписи «REP» рядом с числом репутации, которая всегда на английском независимо от
  языка.

Вывод: разные патч-слои добавляли текст в разное время с разной дисциплиной
локализации — часть текста корректно заведена через `lang==='ru'?ru:en`-тернарники
(видны русские строки), часть добавлена позже уже захардкоженной по-английски без
второго варианта. Итог не читается как «игра на двух языках вперемешку специально», а
как «недособранная локализация» — ровно тот эффект «слеплено из разных эпох патчей»,
который прогнозировался в задаче. **Не исправлено**: это не точечная правка (не один
файл/один селектор), а системная проблема, требующая пройти по десяткам-сотням строк
интерфейса и либо дописать русские варианты, либо осознанно перевести всё на один язык
— средний/крупный объём работы, выходящий за рамки «тривиально и безопасно» из задачи
на эту итерацию. Рекомендация пользователю: решить целевой язык (один язык на релиз,
либо полноценная en/ru-локализация) и поручить это отдельной, специально выделенной
задачей — это самая ценная находка для следующего шага полировки перед релизом.

**Информационная плотность в панели «City & Development»: не исправлено, документировано.**
Строка статистики стадии развития участка (раздел «DEVELOPMENT STAGE») выводит подряд
7 пар «иконка+процент» без подписей: `👥 0/0 · 📄 15 · ⊕ 25% · ⊕ 38% · 🛡 40% · 🎓 39% ·
🔥 37% · 🏛 38% · 🏷 29%` — при этом ДВЕ разные метрики (25% и 38%) используют
ВИЗУАЛЬНО ИДЕНТИЧНУЮ иконку (⊕, круг со крестом внутри), так что на мобильном экране без
возможности навести курсор (тач-устройство, нет hover-подсказки) невозможно понять, что
есть что, не заглянув в код. Панель в целом (11 карточек/секций: Company Reputation,
City Districts, City Simulation, Utilities & Density, Backbone Infrastructure &
Operations, Company Finance, Municipal Bid Board, сама карточка района с Required
Infrastructure и Development Stage) — самая длинная и самая насыщенная цифрами панель
игры (8 шагов прокрутки на весь текст при полном захвате скриншотов). Сама по себе
плотность не выглядит как «стена текста» — почти всё разбито на подписанные карточки
с иконка+заголовок+значение — кроме именно этой одной строки статистики застройки.
**Не исправлено**: чтобы различить одинаковые иконки, нужно либо завести отдельную
уникальную иконку под одну из двух метрик (нужно свериться с `ICON_PATHS_V36`, откуда
берутся все SVG в проекте, и добавить/переназначить одну), либо добавить текстовые
подписи — то и другое требует решения, ЧТО означает каждая метрика (не была тривиально
видна из одного грепа разметки в рамках дизайн-прохода, а гадать в UI-тексте — не
тот риск, который стоит брать негласно). Рекомендация: точечно развести две
одинаковые иконки в этой строке — небольшая, но не «однозначно безопасная без контекста»
правка, оставлена пользователю на отдельный проход.

текстовой меткой («смешанный район» / «конфликт функций» / «специализация») прямо в панели
Land & Zoning — игрок видит последствия выбора без необходимости лезть в код. **Вывод: пункт

### Рекомендации пользователю (не исправлялось в этом проходе — крупнее «тривиально
безопасно» или требует решения, не только правки)

1. **Возможный ценовой «порог» на входе в систему районов.** Первый уровень магистральной
   электростанции/водоканала (`V42_PLANT_COST.power[1]=850`, `.water[1]=720`) плюс первый
   уровень района (`districtUpgradeCost` ранг 1 уровень 1 ≈ 2050💰) плюс районные сети
   (`v41`) — суммарно несколько тысяч монет и десятки досок/бетона ещё до первой покупки
   участка земли, тогда как здания STAGES на этом этапе игры (обычно stageIndex 3-6) стоят
   на порядок меньше (700-3800💰 за штуку). Это не «сломанный» баланс (предыдущий проход
   этой сессии живым кликом подтвердил, что вся цепочка гейтов работает корректно от
   кнопки до кнопки — см. «Закрытие двух оставленных пунктов» выше), и я не нашёл явного
   резкого скачка ВНУТРИ этой подсистемы — но ощущается как заметная ступенька темпа
   ПЕРЕХОДА от «строю по одному зданию» к «развиваю район». Не измерял live-таймингом
   каждый шаг этой ступеньки в реальном времени (это заняло бы отдельный длинный прогон
   ради одного числа) — рекомендую при следующем проходе замерить реальное время от
   разблокировки districts UI до первой купленной земли в честной игре (без чит-инъекции
   денег) и сравнить с ощущением темпа, задокументированным здесь для STAGES.
2. **Зонирование участков (см. выше) уже глубокое** — но тред-офф асимметричен: смешение
   Жильё+Коммерция всегда чистый плюс, конфликт есть только у Жильё+Производство, а
   Коммерция+Производство даёт небольшой плюс без минусов. Значит «всегда мешай Жильё с
   Коммерцией, никогда не клади Производство рядом с Жильём» — это довольно предсказуемая
   доминирующая стратегия, а не постоянное решение с реальной неопределённостью на каждом
   участке. Не трогал: любая правка формулы `districtZoningBalance` — это правка баланса
   взаимосвязанной городской симуляции (налоги/трафик/скорость), которую эта сессия ранее
   явно проверяла как самосогласованную; менять её без полного повторного прогона всей
   цепочки `power`/`water`/`landTax` было бы безответственно в рамках одного прохода.
   Возможное будущее направление (не реализовывать без отдельного дизайн-решения): дать
   Производству небольшой собственный плюс (например, к доходу/бетону/металлу), чтобы
   «всё Производство» стало равноценной по силе, но иной по риску стратегией, а не просто
   более слабым вариантом «всё Жильё+Коммерция».
3. **Очередь toast'ов (`v361PumpToast`, лимит 4 в очереди, минимум 1350-1900мс на
   сообщение) может ронять сообщения при всплеске одновременных событий** (например,
   несколько достижений открываются в один тик вместе с покупкой апгрейда) — поймано
   именно во время тестирования фикса этого прохода (не новая находка, существовавшее
   поведение очереди, просто ранее не проверялось нагрузочно). Для одиночных действий
   игрока (обычный темп кликов) это не проблема — очередь успевает сливаться быстрее, чем
   игрок кликает. Не исправлял: сама очередь — общий механизм показа, используемый
   десятками мест в коде; менять лимит/тайминги без полного прогона всех типов toast'ов
   рискованно для контекста одного прохода. Кандидат для отдельной, специально выделенной
   правки, если разработчик когда-нибудь захочет одновременных burst-уведомлений (например,
   массового зачёта тендера + нескольких достижений сразу).

пример реального «намеренно интернационального» термина, и REP под этот паттерн не
подходит, поскольку у него есть широко используемая русская альтернатива).

4. Строка ~16274 (`claimCityTaskV40`, toast завершения городской задачи, ru-ветка):

### Почему новый блокирующий гейт не добавлялся

Единственный теоретический зазор — доля миллисекунды между синхронным появлением
стройплощадки внутри `purchaseCurrentPad()` (шаг постройки начинается) и

геометрии, задолго до многосекундной анимации стройки) и не является «постройкой без
дороги» в смысле жалобы пользователя (дом навсегда стоящий в чистом поле) — это то,
что и было реальной проблемой, найденной и исправленной в предыдущем проходе. После
фикса `lv=Math.max(1,maxRoadLevelV37())` каждое построенное здание спирали гарантированно
получает дорогу к хабу при следующей пересборке — а пересборка триггерится из ВСЕХ
известных путей создания такого здания (прямая стройка, очередь стройки, загрузка
сейва любого формата). Разработка дальше по пути «сначала дорога» для этой цепочки уже
завершена: логическая зависимость реальна и гарантирована архитектурой, а не только
визуально совпадает. Добавление отдельного блокирующего чека «нельзя строить без
дороги» поверх этого было бы избыточным (второй источник истины для факта, который уже
гарантирован структурой кода) и рискованным без реальной находки — что прямо
запрещено задачей («не форсировать фейковый чек, если честный вывод — что уже
гарантировано»).

### Баг (до фикса)

Ветка `else` (`}else{` строка 14151) внутри v361-версии `toast()` при заполнении
очереди (`v361ToastQueue.length>=4`, строка 14152, до фикса) безусловно делала
`v361ToastQueue.shift()` — выкидывала элемент с индекса 0 вне зависимости от того,
важное это сообщение или нет. Соседняя ветка `if(important&&v361ToastBusy)` (строка
14148) кладёт новые важные сообщения именно в НАЧАЛО массива через `unshift` — то есть
индекс 0 очень часто оказывается именно важным, ещё не показанным сообщением. Из-за
этого безусловный `shift()` прямо противоречил комментарию в том же файле строкой выше
(«Player feedback such as "not enough resources" must not wait behind ambient
messages») — важные сообщения (ошибки, «не хватает ресурсов», достижения, левелапы,
завершения строек) могли молча теряться именно тем путём, который этот комментарий
обещал не допускать, просто НЕ через ту ветку, к которой относится комментарий
буквально (`important&&busy`), а через соседнюю (`else`, ёмкостная эвикция).

## Итерация — закрытие пункта «одинаковая иконка satisfaction/health» из дизайн-аудита (2026-09-22)

строке статистики застройки участка ... нужно сначала выяснить исходный замысел двух
метрик под ⊕, затем развести иконки/подписи». Предыдущая находка описывала эффект
(«⊕» дважды) на глаз со скриншота, без точной привязки к коду — эта итерация нашла
точный источник и проверила его живьём, вместо повторной догадки.

### Метод

`git status`/`git fetch` — рабочее дерево чистое, `HEAD` на `6ff4cab` (фикс очереди
toast, предыдущая итерация). Живой Playwright-тест (iPhone 13 эмуляция) с реальными
кликами `#systemsBtn`→`#openCityBtn` для открытия панели «City & Development» и снятия
живого `outerHTML` первой `.resourceLine` в `#cityGrid` — той самой строки статистики
района из находки дизайн-аудита.

### Находка: источник дублирования — не отсутствие SVG-иконки, а совпадение в самой
эмодзи→иконка карте

`statsLine` (функция построения панели района, строка 9587) выводит 9 сырых эмодзи:
`👥 population/cap · 💼 jobs · ❤️ satisfaction% · 🏥 health% · 🚓 safety% · 🎓
education% · 🚒 fireSafety% · 🚗 traffic% · 🏷️ landValue%`. Эти эмодзи на лету
заменяются на inline SVG патч-слоем v36 (`installIconObserversV36`→`iconizeRootV36`→
`iconizeTextNodeV36`, строки 13767-13783, работает через `MutationObserver` на корневых
UI-контейнерах, включая `cityOverlay`). Замена идёт по карте `EMOJI_ICON_MAP_V36`
(строка 13762) — конкретно `['🏥','health']` И `['❤️','health']` (было, строка
13764) — оба эмодзи указывали на ОДНО имя иконки `'health'` в `ICON_PATHS_V36`
(строка 13746, контур «круг + крест внутри» — буквально то, что описал дизайн-аудит
как «⊕»). Live-DOM подтвердил: до фикса иконки на позиции 2 (satisfaction, ❤️) и
позиции 3 (health, 🏥) в реально отрендеренной строке статистики были байт-в-байт
идентичным `<svg>`-содержимым.

Проверены (python-скрипт по регэкспам обеих секций `EMOJI_ICON_MAP_V36`, включая
дополнение из v36.1-патча строка 13936-13939) ВСЕ остальные случаи, где несколько
эмодзи маппятся на одно имя иконки (`people`, `carry`, `truck`, `cash`, `tender`,
`city`, `growth`, `star`, `team`, `operations`, `park`, `trophy`, `build`, `road`,
`shop`, `school`, `check`) — во всех этих случаях дублирующие эмодзи семантически
синонимичны (несколько вариантов «деньги», несколько вариантов «грузовик», несколько
вариантов «городское здание» и т.д.) и никогда не встречаются РЯДОМ друг с другом в
одной строке UI как отдельные числовые метрики — то есть их совпадающая иконка не
создаёт видимой путаницы для игрока. `health`/`❤️` — единственный случай, где два
семантически РАЗНЫХ значения (эмоциональное удовлетворение жителей и здравоохранение)
оказывались рядом в одной строке с одинаковой иконкой.

### Фикс

`ICON_PATHS_V36` (строка 13746-13747 после правки): добавлена новая запись `heart` —
простой контур сердца, тем же стилем обводки, что и остальные иконки набора (viewBox
24×24, `stroke`-путь без заливки, как и все соседние). `EMOJI_ICON_MAP_V36` (строка
13764): `['❤️','health']` → `['❤️','heart']`. `🏥`/`⚕️` не тронуты, по-прежнему `'health'`.
Итого 2 изменённые строки в файле. Не тронуто: сам механизм `iconizeRootV36`/
`MutationObserver`, любая другая запись в обеих картах, сама строка `statsLine`
(строка 9587, порядок и состав метрик), любая игровая логика/экономика.

### Живая проверка (Playwright, iPhone 13 эмуляция, `chromium.launch`
`executablePath:'/opt/pw-browsers/chromium'`, `args:['--use-gl=swiftshader',
'--enable-webgl','--ignore-gpu-blocklist']`, `python3 -m http.server`)

1. Синтаксис: все 13 inline `<script>`-блоков файла прошли `node --check` без ошибок

### Методологическая ловушка первого прохода — и как её обошли

Первый (черновой) проход капчурил текст напрямую: `page.evaluate(() => { lang = L; try {
renderXPanel(); } catch{} })`, без вызова `applyLanguage()`, как явно разрешено формулировкой
задачи («re-render that panel's render function ... call the live one»). Результат содержал
одно ложное срабатывание: слово «Achievements» присутствовало в ОБОИХ языковых дампах
панели достижений. Диагностика: `document.getElementById('achTitleText').textContent =
t('ach_title')` (строка 9023) живёт ВНУТРИ `applyLanguage()`, а не внутри `renderAchList()`
(строка 7656) — заголовок панели обновляется только при полном цикле переключения языка,
не при повторном вызове render-функции самой по себе. Прямой вызов `renderAchList()` без
предварительного `applyLanguage()` в моём тестовом скрипте не подтягивал заголовок — ровно
та же методологическая ловушка «наблюдение без реального тумблера», которая уже дала одно
ложное срабатывание дизайн-аудита (панель достижений «полностью на английском» — итерация 8
это опровергла) и чуть не дала второе здесь.

Исправлено переходом на честный проход: реальный `page.click('#langBtn')` перед каждым
открытием панели (а не запись в `lang` напрямую). Попутно обнаружено: пока открыта любая
панель (`.show` на `systemsOverlay`/`metaOverlay`/etc, z-index 40, `position:fixed;
inset:0`), кнопка `#langBtn` физически недоступна для клика — Playwright возвращает
`<div class="v30Head">… subtree intercepts pointer events`. Это не баг, а следствие того,
что `#langBtn` живёт в верхнем HUD-баре под оверлеем: реальный пользователь тоже не может
нажать её, пока открыта модалка, — то есть «переключить язык, затем открыть панель» является
ЕДИНСТВЕННЫМ реалистичным путём пользователя, и именно он тестировался (закрыть все
оверлеи → переключить язык кликом → открыть нужную панель → снять дамп). Повторный дамп
этим методом не дал ложных срабатываний ни для одной из 11 панелей.
