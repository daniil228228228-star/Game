## P0-НАХОДКА №1 (найдена уже при boot-тесте импорта, не отдельным проходом аудита)

**Место**: `tycoon-v62.html`, слой `v58-road-geometry-pass` (тег `<script
id="v58-road-geometry-pass">`, начинается строка 27614), функция `refreshAllRoadsV58`
(строка 27787) внутри обёртки `safe58` (строка 27617): `safe58(()=>
refreshRoadMaterialsV57?.())`.

**Проявление**: при каждой загрузке страницы в консоль **трижды** (соответствует
тройному вызову `refreshAllRoadsV58` из своего `init` — немедленно + через 450мс +
через 1400мс, тот же паттерн, что и в соседнем слое v57) падает:
```
[v58 roads] ReferenceError: refreshRoadMaterialsV57 is not defined
    at tycoon-v62.html:27614:37
    at safe58 (tycoon-v62.html:27617:34)
    at refreshAllRoadsV58 (tycoon-v62.html:27787:5)
```

**Первопричина**: `refreshRoadMaterialsV57` реально существует (строка 27377), но
объявлена **внутри собственной IIFE-обёртки слоя v57** (`(()=>{ ... })()`, строки
~27200-27611) — типичный паттерн этого файла: каждый патч-слой v56-v62 изолирован в
свой замыкающий IIFE, а не просто дописан в глобальный scope, как более старые слои
v30-v45. Слой v57 экспортирует наружу через `window.__TYCOON_ROAD_AUDIT_V57__` только
`{run, refresh}` (строка 27603) — САМУ функцию `refreshRoadMaterialsV57` наружу не
пробрасывает. Слой v58 (отдельная, более поздняя IIFE) пытается вызвать её как
глобальную по голому имени — но такого глобала не существует, поэтому уже само
обращение к идентификатору (`refreshRoadMaterialsV57?.()` — опциональная цепочка НЕ
спасает от `ReferenceError` при обращении к необъявленному имени, она защищает только
от `undefined`/`null` у уже существующего значения) бросает исключение. `safe58` ловит
его и логирует, поэтому игра не падает целиком (fail-soft), но:
1. Материалы дорог, которые должен был обновить этот вызов, **никогда не обновляются**
   этим конкретным путём.
2. Три одинаковые ошибки в консоли при каждой загрузке — заметный шум для
   отладки/QA, прямо противоречит цели файла («QA Polished»).

**Это ровно тот класс проблемы, который просил найти раздел 2 ТЗ** («конфликтующие
runtime-патчи», «функции, переопределённые/недоступные между слоями», «один фикс
исправляет проблему, следующий её снова ломает») — здесь не переопределение, а
частный случай той же болезни: слой v58 писался в предположении, что v57 выставляет
свою функцию глобально (как делали более старые слои v30-v45), но новый
IIFE-паттерн v56+ это предположение нарушает.

**Правильное решение (не применено — это audit-only проход)**: либо (а) слою v57
явно пробросить `window.refreshRoadMaterialsV57 = refreshRoadMaterialsV57;` (или
включить её в уже существующий `window.__TYCOON_ROAD_AUDIT_V57__` объект как ещё одно
поле, например `.refreshMaterials`), либо (б) слою v58 вызывать через уже
существующий публичный интерфейс `window.__TYCOON_ROAD_AUDIT_V57__?.refresh?.()`
вместо прямого имени несуществующей глобальной функции — see риск ниже.

**Риск исправления**: низкий сам по себе (добавить один `window.X = X` или
переключить один call site на уже существующий публичный метод) — НО нужно сначала
проверить, что оба слоя (v57 и v58) не ожидают РАЗНОЕ поведение под одним и тем же
именем (v57's `refreshRoadMaterialsV57` может по смыслу отличаться от того, что делает
`window.__TYCOON_ROAD_AUDIT_V57__.refresh`, который скорее всего=`refreshAllRoadsV57`,
не именно materials-only функция) — то есть решение (б) может незаметно поменять
СЕМАНТИКУ вызова (обновить всю сеть дорог целиком вместо только материалов), а не
просто починить симптом. Это войдёт в детальный анализ архитектуры (раздел 2) в
следующем проходе — здесь зафиксировано как находка, не фикс.

### Находки — Раздел 1 (Запуск и стабильность)

**[P0] Находка №1 (уже в документе выше) — реконфирмирована живым тестом**
- Живой прогон подтвердил: ровно 3 идентичные `[v58 roads] ReferenceError:
  refreshRoadMaterialsV57 is not defined` на каждой из 6 протестированных загрузок
  (чистая загрузка, загрузка со старым сейвом, 4 подряд перезагрузки) — 0
  `pageerror`, 0 роста количества ошибок между перезагрузками (не накапливается,
  не ухудшается). Других находок по этому конкретному классу («бросить
  ReferenceError на голое имя функции, объявленной внутри чужого IIFE») в
  v56-v62 не обнаружено — `refreshRoadMaterialsV57` единственная функция такого
  рода, которая вообще осталась недостижимой извне (остальные функции с похожей
  судьбой либо не вызываются другими слоями по голому имени, либо явно
  экспортированы через `window.__TYCOON_ROAD_AUDIT_V5x__`).

**[P1] Регрессия качества рендера на iPhone — фикс v55 не унаследован в линии v56-v62**
- Место: `tycoon-v62.html:1692-1701` (создание `renderer`, константы
  `MAX_RENDER_DPR`/`MIN_RENDER_DPR`), дублируется в `rendererPolishV45()`
  (`tycoon-v62.html:25131-25140`, слой между v44 и v46, вызывается из `bootV45()`
  при каждой загрузке).
- Проявление: живое чтение состояния `renderer` на iPhone 13 эмуляции после полной
  загрузки —
  ```json
  {
    "V54_IOS_STABILITY": true,
    "antialias": false,
    "shadowMapEnabled": false,
    "shadowMapType": 0
  }
  ```
  `antialias` прочитан через `renderer.getContext().getContextAttributes().antialias`
  — это неизменяемый параметр WebGL-контекста, зафиксированный в момент его
  создания (`new THREE.WebGLRenderer({antialias: !V54_IOS_STABILITY, ...})`,
  строка 1693) и принципиально не может быть исправлен никаким более поздним
  патч-слоем во время выполнения. Значения (`antialias:false`,
  `powerPreference:'default'`, `MAX_RENDER_DPR` зажат до `1.15`, `MIN_RENDER_DPR`
  до `0.85`, тени выключены с заглушкой `BasicShadowMap`) **побайтово совпадают**
  с кодом, который эта же сессия ранее уже находила и явно чинила в
  `TYCOON_V55_PLAN.md` (раздел «Итерация — смягчение принудительного урезания
  качества рендера на iPhone», подтверждённый живой проверкой на той же iPhone
  13 эмуляции: `antialias:true, shadowMapEnabled:true, shadowMapType:1,
  maxDpr:1.5, minDpr:1.08`).
- Первопричина: файл `tycoon-v62.html`, присланный пользователем, — это
  отдельная линия внешней разработки (v56-v62 патчи поверх какой-то версии v55),
  которая **не унаследовала** локальный фикс, сделанный в этой сессии поверх
  `tycoon-v55.html`. Другими словами, внешний разработчик, скорее всего,
  продолжал работу от исходного «v55 Stability Corrective» (до того, как эта
  сессия сняла принудительное урезание для iPhone), а не от уже исправленной
  копии. Ни один из патч-слоёв v43-v62 не убирает ветку `V54_IOS_STABILITY` из
  базовой инициализации рендерера — она осталась ровно в исходном,
  «зарезанном» состоянии.
- Побочный эффект: слой v56 (`improveRenderer()`, строка 27084-27096) пытается
  частично компенсировать это — принудительно включает
  `renderer.shadowMap.enabled=true` и поднимает DPR через
  `renderer.setPixelRatio(Math.max(1.5,targetDpr))`, игнорируя константы
  `MIN/MAX_RENDER_DPR`. Но живой замер (`renderer.getPixelRatio()===2`,
  `shadowMap.enabled===false`, 3+ секунды после загрузки) показывает, что
  **итоговое состояние — тени всё равно выключены**, а DPR оказывается в
  противоречивом состоянии: выше своего же формального `MAX_RENDER_DPR=1.15`,
  но без теней и без antialiasing. Порядок исполнения: `rendererPolishV45()`
  вызывается из `bootV45()` через `setTimeout(bootV45,140)`, зарегистрированный
  на `DOMContentLoaded` раньше v56, но с задержкой 140мс — то есть после
  синхронного `v56.init()` (тот срабатывает прямо в момент события
  `DOMContentLoaded`, без задержки) он снова гасит тени; в теории v56-й
  `setTimeout(...,350)`/`setTimeout(...,1200)` должны включить их обратно
  позже, но живой замер этого не подтверждает (возможно, из-за пересечения с
  watchdog `V54_STABILITY`, см. следующую находку, либо из-за реального порядка
  срабатывания таймеров под нагрузкой при парсинге файла в 28600 строк). В
  любом случае результат нестабилен и непредсказуем — конечное качество
  рендера на iPhone зависит от гонки между как минимум 3 независимыми участками
  кода (`rendererPolishV45`, `v56.improveRenderer`×3, watchdog `V54_STABILITY`),
  ни один из которых не знает о существовании других.
- Правильное решение: применить тот же фикс, что уже задокументирован и
  проверен в `TYCOON_V55_PLAN.md`, к базовому коду `tycoon-v62.html` — убрать
  ветвление по `V54_IOS_STABILITY` из инициализации `renderer` (строки
  1692-1701) и из `rendererPolishV45()` (строки 25134-25135), оставив сам
  watchdog (`V54_STABILITY`/`emergencyLoopV54`) нетронутым как аварийный
  fallback. После этого разобраться, нужен ли вообще `v56.improveRenderer()` —
  скорее всего да (он также трогает освещение/материалы), но его блок про DPR/
  тени станет избыточным дублированием базового фикса и его стоит убрать,
  чтобы не оставлять двух источников истины для одних и тех же настроек.
- Риск исправления: низкий с точки зрения корректности (это уже проверенный
  фикс), но нужно заново прогнать живую проверку производительности на iPhone
  13 эмуляции после объединения с изменениями v56-v59 (усиленные тени
  3072×3072, `castShadow` почти для всех мешей с `position.y>0.18` — строка
  27135) — сочетание «убрать throttling» + «v56 требует более тяжёлые тени» может
  оказаться тяжелее, чем то, что проверялось в v55.

**[P1] v56 навсегда отключает адаптивную подстройку качества рендера по живому FPS**
- Место: `tycoon-v62.html:27087` — `if(typeof tuneRenderResolution==='function')
  tuneRenderResolution = function(){};` внутри `improveRenderer()` (слой v56).
  Оригинальная функция — `tycoon-v62.html:12341-12361`, вызывается **каждый
  кадр** из основного игрового цикла (`safeFrameCallV54('tuneRenderResolution',
  ()=>tuneRenderResolution(dt))`, строка 12403).
- Проявление: `tuneRenderResolution` — единственный механизм, который следит за
  реальным временем кадра (`avgMs`) и снижает `renderDpr` до `MIN_RENDER_DPR`
  при просадке FPS (>24.5мс/кадр) или поднимает до `MAX_RENDER_DPR` при запасе.
  Живой тест подтверждает: `tuneRenderResolution.toString()` после полной
  загрузки на iPhone 13 эмуляции равен буквально `"function(){}"` — пустая
  функция-заглушка. Слой v56 перезаписывает саму переменную (не просто её
  поведение), поэтому это необратимо для всех последующих кадров сессии — ни
  один более поздний слой (v57-v62) её не восстанавливает (проверено грепом:
  `tuneRenderResolution` больше нигде не переопределяется).
- Первопричина: v56 одновременно (а) принудительно поднимает DPR/качество
  («улучшить картинку») и (б) отключает единственный механизм, который мог бы
  опустить это качество обратно, если реальное устройство не тянет. Похоже на
  намеренное решение автора патча («хочу зафиксировать высокое качество»), но
  без замены на альтернативный, более мягкий адаптивный механизм.
- Правильное решение: не глушить `tuneRenderResolution` целиком — либо поднять
  его `MIN_RENDER_DPR`/`MAX_RENDER_DPR` (если цель v56 — просто задать более

- Риск исправления: средний — нужно заново откалибровать пороги `avgMs`/шаги

  `.stageRoads`) делает `scene.remove()` + `disposeObject3D()` +
  пересоздание group с десятками мешей — всё это в первые ~2 секунды после
  `DOMContentLoaded`, наложенное на и без того тяжёлый первый кадр (543
  объекта в сцене сразу после загрузки, по логам boot-теста). Комментарий
  самого v62 прямо признаёт эту проблему постфактум: `/* Road geometry changes
  only on refresh. Clean it there, not every 650 ms. */` (строка 28573) — v62
  сам отказывается от периодического опроса в пользу событийной модели
  (`wrapRefresh62`), но не трогает уже существующий тройной boot-каскад ни в
  себе, ни в предыдущих 6 слоях.
- Первопричина: каждый новый патч-слой добавлялся независимо, по шаблону
  «на всякий случай перестрахуемся — вызовем ещё раз через 500мс, а то вдруг
  сцена не успела прогрузиться» — без координации с уже существующими такими
  же тройными вызовами в предыдущих слоях. Тройной вызов одного слоя может
  быть оправдан (например, ждём асинхронной загрузки текстур), но 7
  независимых слоёв, делающих это одновременно поверх одной и той же
  дорожной сети, дают экспоненциально избыточную работу.
- Правильное решение: единая точка входа — один координирующий
  `refreshAllRoadNetworks()` (возможно, обёртка над уже существующим
  `wrapRefresh62`-подходом v62, но примененная ко ВСЕМ семи слоям сразу, а не
  только к пяти конкретным функциям), вызываемая по событию «мир готов»
  (после первой полной инициализации), плюс, если действительно нужна
  повторная проверка из-за гонки асинхронной загрузки, — одна отложенная
  проверка с формальным условием готовности (например, `texturesLoaded &&
  citySceneReady`), а не слепые `setTimeout` на случайных интервалах.
- Риск исправления: средний-высокий — семь слоёв реализуют разную геометрию
  дорог с разными версиями одних и тех же функций (см. карту переопределений
  ниже), и живые версии этих функций постоянно меняли поведение друг друга по
  ходу разработки; нужно точно определить, какая версия каждой функции
  реально используется СЕЙЧАС (карта ниже), прежде чем убирать «лишние»
  вызовы — иначе можно случайно убрать единственный вызов, который реально
  достигает актуальной (последней переопределённой) версии функции.

     худшем случае они могут мешать друг другу сходиться, хотя оба
     по отдельности выглядят безопасными (fail-soft, идемпотентны).
  2. **Три независимых механизма синхронизации видимости онбординг-объектов**
     (`fieldUpgradePads`, `sawmillDropoff`, `sourceTrees`) по признаку раннего
     этапа игры (`stageIndex<2`): `syncOnboardingObjects()` (v60),
     `syncTutorialWorld61()` (v61, делает более полную версию той же логики —
     плюс управление деревьями/`sourceTrees`), `syncCoreAssets62()` (v62, ещё
     одна, третья версия той же идеи, плюс управление `populationStat`). Все
     три выполняют пересекающуюся работу на трёх разных интервалах бессрочно.
- Первопричина: тот же паттерн, что и в предыдущей находке — каждый новый
  патч-слой добавлял свой независимый «сторож», не переиспользуя и не отменяя
  уже существующий от предыдущего слоя. Поскольку все слои — IIFE с приватными
  функциями и WeakMap, у более позднего слоя физически нет доступа к
  внутреннему состоянию более раннего, чтобы его переиспользовать или явно
  остановить (`clearInterval` не вызывается нигде для этих трёх таймеров).
- Правильное решение: оставить только последнюю, самую полную версию каждой
  задачи (repairWorkers62 для рабочих — она добавляет проверку
  `targetInsideObstacle62`, которой нет в v60; syncCoreAssets62 для
  онбординга — она самая полная), и явно `clearInterval` двух более ранних
  циклов при инициализации более позднего слоя (либо просто удалить старые
  `setInterval`-вызовы из v60/v61, раз их функциональность полностью
  покрыта v62 — но см. риск ниже).
- Риск исправления: `syncTutorialWorld61()` управляет и `sourceTrees`
  (видимостью деревьев для этапа лесозаготовки), а `syncCoreAssets62()` — нет
  (её версия сфера ответственности уже, только `fieldUpgradePads`/
  `sawmillDropoff`/`populationStat`/`carriedLogs`-индикатор). Простое удаление
  v61-интервала в пользу только v62-го **отключит логику видимости деревьев**
  на раннем этапе — нужно перенести именно эту часть в финальную версию, а не
  слепо выбрасывать «более старую» функцию целиком.

### Находки — Раздел 2 (Архитектура кода)

**[P2] Тройной дублирующийся MutationObserver «причесать кнопки/панели» (v47, v48, v49)**
- Место:
  - v47 `installPanelComfortV47()`, `tycoon-v62.html:25623-25627`: наблюдает
    `document.body{subtree:true,childList:true}`, на каждый добавленный узел
    ищет `.v30Panel,#achPanel,#hintCard` (ставит `scrollbarGutter='stable'`) и
    `.v30Btn` (ставит `type='button'`, если не задан).
  - v48 `installPanelDensityComfort()`, `tycoon-v62.html:25882-25888`:
    наблюдает `document.body{childList:true,subtree:true}`, ищет `.v30Btn`
    (ставит `title` из длинного `textContent`) и `.v30Panel` (ставит
    `aria-modal='true'`).
  - v49 `installPanelQualityV49()`, `tycoon-v62.html:26058-26060`: наблюдает
    `document.body{subtree:true,childList:true}`, ищет `.v30Panel` (ставит
    `aria-modal='true'`, `overflowAnchor='none'`) и `.v30Btn,button` (ставит
    `type='button'`).
- Проявление: три независимых `MutationObserver`, все три навешены на
  `document.body` с одинаковыми опциями (`subtree:true, childList:true`),
  все три реагируют на КАЖДУЮ вставку DOM-узла в документе (любой toast,
  любое открытие панели, любой ре-рендер `innerHTML` — а таких вставок в этой
  игре очень много: HUD обновляется каждый кадр/тик, панели типа
  `renderFleetPanel`/`renderFleetOperations` целиком перезаписывают
  `innerHTML` при каждом открытии). Их работа пересекается почти полностью:
  `type='button'` ставится и в v47, и в v49 (на один и тот же `.v30Btn`);
  `aria-modal='true'` ставится и в v48, и в v49 (на один и тот же `.v30Panel`).
  Итого на каждую вставку DOM-узла в `document.body` срабатывают 3
  независимых полных обхода поддерева через `querySelectorAll`, из которых
  минимум 2 делают буквально одинаковую работу впустую (повторно
  устанавливают уже установленный атрибут).
- Первопричина: типичный для этой кодовой базы паттерн «патч-слой добавляет
  свой собственный наблюдатель, не проверяя, не решена ли уже эта же задача
  предыдущим слоем» — усугубляется тем, что v47/v48/v49 не знают о работе
  друг друга (каждый в своей IIFE), поэтому не могут просто расширить уже
  существующий наблюдатель.
- Правильное решение: объединить в один наблюдатель на `document.body`,
  который на каждой вставке делает один проход и применяет все нужные
  атрибуты (`type='button'`, `aria-modal='true'`, `overflowAnchor='none'`,
  `scrollbarGutter='stable'`, `title` для длинных кнопок) — по сути,
  объединить `apply()`/`decorate()` из всех трёх функций в одну. Это не
  единственные подобные наблюдатели в файле — всего в `tycoon-v62.html`
  13 отдельных `new MutationObserver(...)` (грепом), из которых как минимум
  ещё 2 (v44Runtime.observer на `document.body`, строка 24560; и v36-й
  построчный наблюдатель на каждый `UI_ROOT_IDS_V36`, строка 13789) тоже
  делают DOM-декорирование по факту вставки узлов — их тоже стоит
  рассмотреть на предмет объединения в следующем полном проходе по
  разделу 12 (UI/UX)/18 (cleanup), но подробный разбор каждого не входил в
  текущий объём (разделы 1-2).
- Риск исправления: низкий — все три делают идемпотентные, чисто
  косметические/accessibility правки (устанавливают атрибуты, не меняют
  структуру DOM и не читают состояние игры), объединение в теории безопасно;
  риск скорее в порядке применения (например, если объединённая функция
  должна успеть отработать до какого-то другого кода, читающего эти
  атрибуты) — стоит явно проверить оба места (`v47-action-focus`,
  `v48-blocked` классы), которые ЧИТАЮТ состояние DOM, установленное соседними
  наблюдателями, на предмет гонок при рефакторинге.

**[P3] Мёртвый код — `addRoadJointV38` больше не вызывается ни из одного живого пути**
- Место: базовое объявление `tycoon-v62.html:15664`, переопределения в v56
  (`27335`) и v57 (`27413`, финальная живая версия функции).
- Проявление: грепом найдены все 7 мест вызова `addRoadJointV38(...)` во всём
  файле (строки 15692, 15693, 15717, 27519, 27540, 27542, 28196) — **каждое**
  из них находится внутри тела функции (`refreshArterialRoads`,
  `makeStageRoadGroupV367`, `makeCityStreetGroup` — в их версиях от base/v57/
  v60 соответственно), которая сама была переопределена более поздним слоем
  и больше не является живой версией этой функции (финальные живые версии —
  `refreshArterialRoads`=v59, `makeStageRoadGroupV367`=v61,
  `makeCityStreetGroup`=v59/v61-обёртка — см. карту ниже, ни одна из них не
  вызывает `addRoadJointV38`, все используют более новые
  `addIntersection58`/`addIntersection59`/`addJunction61`). Значит функция
  `addRoadJointV38`, хоть и дважды переопределялась (что само по себе
  выглядит как «активно поддерживаемый код»), фактически не вызывается НИ
  ОТКУДА в текущем рантайме v62.
- Первопричина: классический побочный эффект того, что каждый новый
  дорожный патч-слой писал СВОЮ версию не только конечных «сборочных»
  функций (`makeCityStreetGroup` и т.п.), но и попутно менял то, какие
  низкоуровневые хелперы эти сборочные функции вызывают внутри себя — то
  есть смена реализации `makeCityStreetGroup` в v58 незаметно «осиротила»
  вызовы `addRoadJointV38`, которые раньше шли из v57-й версии той же
  функции.
- Правильное решение: удалить (или явно пометить `@deprecated` до полного
  разбора раздела 4) — это чистая функция без побочных эффектов на глобальное
  состояние вне переданной ей `group`, безопасна для удаления после
  двойной проверки грепом непосредственно перед фиксом (список вызовов может
  измениться в будущих патчах раздела 4).
- Риск исправления: очень низкий (мёртвый код, 0 живых вызовов подтверждено
  грепом по всем 28592 строкам) — единственный риск в том, что раздел 4
  (отдельный глубокий аудит дорог) может заново использовать эту функцию как
  референс при написании плана v63; стоит просто оставить как есть до
  решения по разделу 4, а не удалять прямо сейчас (аудит-only проход и так не
  вносит правки).

**[P3] Три отдельных обработчика клика на одной кнопке `#resetBtn` вместо одного**
- Место: `tycoon-v62.html:16499` (слой V40), `:16931` (слой V41), `:17325`
  (слой V42) — каждый вида:
  ```js
  const resetBtnV4X=document.getElementById('resetBtn');
  if(resetBtnV4X)resetBtnV4X.addEventListener('click',()=>{
    if(suppressAutoSaveV36)try{localStorage.removeItem(V4X_STATE_KEY);}catch(e){}
  },{capture:false});
  ```
- Проявление: не баг (DOM корректно поддерживает много листенеров на одном
  событии/элементе, все три срабатывают, живой тест подтверждает
  `tycoon3d_save_v3` и связанные ключи действительно очищаются на reset) — но
  это явное дублирование одного и того же шаблона 3 раза подряд вместо
  одного цикла по массиву ключей `[V40_STATE_KEY, V41_STATE_KEY,
  V42_STATE_KEY]`. Чисто эстетическая/поддерживаемостная находка, не влияет
  на игру.
- Первопричина: каждый слой (v40, v41, v42) добавлял свой собственный
  локальный кэш состояния города и, соответственно, свою же логику очистки
  этого кэша при reset — без рефакторинга в сторону уже существующего
  паттерна двух своих предшественников.
- Правильное решение: объединить в один обработчик, чистящий список ключей.
- Риск исправления: минимальный — три отдельных ключа localStorage,
  объединение обработчиков не меняет, какие ключи чистятся, только структуру
  кода.

**[P2] Архитектурное наблюдение (не находка сама по себе, контекст для раздела 4) — v59 резко меняет масштаб ширины дорог**
- Место: `ROAD59.widths`, `tycoon-v62.html:27849-27858` — например,
  `perimeter:[0,2.62,2.78,2.96]` против `mainW=[0,1.28,1.50,1.72]` в v56
  (`27174-27180` контекст) и `mainW=[0,1.32,1.54,1.78]` в v58
  (`27726`) — **v59 увеличивает ширину дорог этого типа более чем в 2 раза**
  относительно того, что делали два предыдущих слоя буквально несколько
  «версий» назад в том же файле, с обоснованием в комментарии
  (`27934`: «no road slab may be narrower than a full-size truck plus
  clearance»). Это не находка «баг», а фиксация факта для раздела 4
  (отдельный аудит дорожной системы, вне объёма этого прохода) — резкая
  смена фундаментальной константы масштаба в позднем патч-слое подпадает
  под тот же архитектурный паттерн «конфликтующие раннтайм-патчи», который
  просил найти раздел 2, но полноценная оценка последствий (не полезли ли
  дороги такой ширины на здания/тротуары/статические коллайдеры) требует
  геометрического анализа мира, который является предметом раздела 4, а не
  раздела 1-2. Зафиксировано здесь, чтобы следующий проход по разделу 4 не
  начинал поиск этого несоответствия с нуля.

ориентация и 4 подряд перезагрузки — без регрессий, все ранее задокументированные

новых слоёв. Карта переопределений выше покрывает 24 функции/системы,
затронутые v56-v62, и предназначена как справочный материал для всех
последующих проходов (особенно раздела 4 — дорожная система, где эта карта
должна съэкономить много времени на повторный грепинг тех же цепочек).

находка в v56-v62 самих по себе, а то, что базовый (до-патчевый) код
`tycoon-v62.html`, к которому эти патчи прикладываются, потерял уже
проверенный и задокументированный в этом же репозитории фикс качества
рендера на iPhone. Это значит, что план v63 должен начинаться не с
очередного patch-слоя поверх v62, а с явной сверки базового кода v62 против
уже сделанной работы по линии v55, а не считать, что «более новый файл»
автоматически означает «более новый = включает все старые фиксы».

**[P1] `distToNearestRoadSegment` покрывает только STAGE-магистраль — «страховочная сетка» от построек поверх районных дорог фактически не работает**

  перебирает ТОЛЬКО полилинии stage-спирали. Базовая (до-v56) версия,
  `tycoon-v62.html:2431-2442`, имела ровно то же ограничение (перебирала
  только `pathPoints`, тот же спинной хребет под другим именем) — это не
  новая регрессия v56-v62, а унаследованный от базового кода пробел,
  который v61, переписывая функцию заново ради интеграции с новым
  `planStageRoute61`, не расширил, хотя в файле уже существует (и
  используется в другом месте) правильный, широкий аналог —
  `distToNearestRoadNetworkV369` (`tycoon-v62.html:15218-15235`, учитывает
  master-дороги + районные артерии + периметр/крест/локальную сетку каждого
  района).
  Единственный живой потребитель узкой функции, который явно предназначен
  как страховочная сетка от пересечения дорога/здание — `roadOverlap`-проверка
  внутри `auditV342LandIntegrity()`, `tycoon-v62.html:12700`:
  `const roadOverlap=distToNearestRoadSegment(p.pos.x,p.pos.z)<1.85;`.
- Проявление: живой тест — точка на осевой линии периметральной улицы
  района (не на stage-спирали) даёт кардинально разные ответы от двух
  функций:
  ```json
  {"district":"waterfront","onStreetCenterline":[-42,33.6],
   "narrow":11.83,"broad":0}
  ```
  (`broad`=`distToNearestRoadNetworkV369`, корректно определяет «на дороге»;
  `narrow`=`distToNearestRoadSegment`, сообщает 11.83 юнита — «далеко от
  дороги», хотя точка физически стоит на асфальте). Прямой тест самой
  страховочной функции: участок земли района `suburb` принудительно
  выставлен точно на осевую линию его собственной периметральной улицы
  (`forcedPos:{x:-46,z:-38.1}`), после чего вызвана реальная живая
  `auditV342LandIntegrity()` — участок **не был перемещён/исправлен**
  (`"wasRepositioned": false`, позиция `before`/`after` идентична).
- Первопричина: в файле сосуществуют два независимых «расстояние до
  дороги»-хелпера с разным охватом (узкий — только stage-спираль; широкий —
  вся сеть), и разные части кодовой базы вызывают их непоследовательно.
  Место, которое РЕАЛЬНО размещает новые участки
  (`landPlotWorldPosition`, `tycoon-v62.html:10688-10720`, кольцевой поиск
  строка 10706), корректно использует широкую `distToNearestRoadNetworkV369`
  — поэтому на практике участки размещаются верно (живой тест плейсмента:
  все реальные позиции 6-9+ юнитов от ближайшей дороги по широкой метрике).
  Но «страховочная сетка», которая должна ПЕРИОДИЧЕСКИ перепроверять уже
  расставленные позиции и чинить испорченные (например, после смены схемы
  района, после миграции старого сейва, или после будущего бага в другом
  месте), использует узкую функцию и поэтому никогда не сможет обнаружить
  «участок оказался на районной/артериальной дороге» — только «участок
  оказался на stage-спирали», что при типичном расположении районов
  (30-50 юнитов от центра, вне охвата спирали) почти никогда не
  происходит физически. Ровно тот класс архитектурной проблемы,
  который просил найти раздел 4 («дублирующиеся хелперы, которые должны
  быть одним источником истины») и общий инвариант «геометрия дороги /
  геометрия навигации должны описывать одну и ту же сеть» — здесь
  геометрия для отрисовки использует широкую сеть, а часть логики
  безопасности — узкую.
- Правильное решение: заменить `distToNearestRoadSegment(p.pos.x,p.pos.z)`
  на `distToNearestRoadNetworkV369(p.pos.x,p.pos.z)` в
  `auditV342LandIntegrity()` (строка 12700). Также стоит грепом
  перепроверить остальные ~15 живых вызовов `distToNearestRoadSegment` по
  всему файлу (декор/сценарий, `player`-пыль под ногами, `roadOverlap` у
  системы трафика — строка 12700 сама попала в оба списка) — часть из них
  (например, разовый `scatterScenery()` на строке 2444, выполняющийся до
  разблокировки районов) действительно не нуждается в широком охвате и
  может остаться как есть, но каждый нужно явно проверить, а не менять
  оптом.
- Риск исправления: низкий для самого фикса (замена одного имени функции в
  одном месте) — но `distToNearestRoadNetworkV369` заметно дороже по CPU
  (перебирает узлы всех разблокированных районов + мастер-дороги на каждый
  вызов, без кэша), а `auditV342LandIntegrity()` может вызываться на
  каждую загрузку/миграцию сейва для потенциально многих участков сразу
  (`LAND_PLOTS_PER_DISTRICT × 4 района`) — при большом количестве районов
  на позднем этапе прогрессии стоит заранее проверить, не создаёт ли это
  заметный джанк на слабых мобильных устройствах (раздел 3,
  производительность, вне объёма этого прохода, но стоит передать туда).

  отчёте указывает не на реальную дорогу, а на мёртвый объект.
  Дополнительно оба этих аудита (плюс v59-й) сообщают ложное
  `duplicates:[{group:'stage',count:16,...}]` / `checks.noExactDuplicates:
  false` — прямая проверка реальных мировых `Box3` этих 16 мешей
  (`tycoon-v62.html`, замер через `road_audit3.mjs`) показывает 4 РАЗНЫЕ
  мировые позиции (например, центр одного меша `[1.215, 39.988]`, другого
  — `[35.053, 7.958]` — явно разные районы), не стек одинаковых объектов.
  Причина ложного срабатывания: сигнатурная функция дублей строится из
  `o.position.x/y/z` + `o.geometry.parameters` — но 16 отмеченных мешей
  это `BufferGeometry`-ленты из `ribbon61()` (`tycoon-v62.html:28378-28393`,
  кривые повороты stage-дороги, введены только в v61), у которых
  `.geometry.parameters` не существует (не параметрическая геометрия — все
  координаты запечены прямо в буфер вершин в мировых координатах), а
  `.position` мешей-лент всегда `(0,0,0)` — то есть сигнатура одинаковая у
  ВСЕХ таких мешей независимо от их реального положения.
- Первопричина: три независимых аудит-инструмента (v57, v58, отчасти v59)
  писались против той версии дорожной сети, что существовала на момент
  ИХ СОБСТВЕННОГО слоя, и ни разу не обновлялись при появлении более
  поздних слоёв, которые меняли теги/типы геометрии. Дублирующий
  детектор писался ещё до того, как в файле появилась первая
  `BufferGeometry`-геометрия дороги (введена только в v61) — типичный
  «мы не знали, что будущий код будет таким» пробел, не ошибка на
  момент написания.
- Правильное решение: либо удалить v57/v58-е аудиты как мёртвый
  инструмент (раз v59-й/v61-й/v62-й их полностью замещают и дополняют),
  либо явно пометить их вывод как relevant only for the tags their own
  layer creates (переименовать поля так, чтобы не выглядело как «аудит
  всей дорожной сети»). Для сигнатурного детектора дублей — во всех трёх
  местах, где он есть — добавить fallback на `geometry.boundingBox`/
  вычисленный `Box3` центра меша для геометрий без `.parameters`, вместо
  использования сырых локальных `position`/`parameters`.
- Риск исправления: низкий (это сами QA-инструменты, не игровая
  логика) — но пока это не исправлено, разработчик, ориентирующийся на
  `checks.noExactDuplicates` в v57/v58/v59, будет либо получать вечный
  ложный «есть дубли» (шум, скрывающий реальные будущие проблемы), либо
  ложное куда более опасное впечатление «декор/бордюр/перекрёстки v57/v58
  проверены и в порядке» там, где эти проверки физически ничего не видят.

**[P3] Зазор 0.025 юнита между бордюром и тротуаром на каждом районном/артериальном сегменте с обоими элементами**
- Место: `addRoadDeck59()`, `tycoon-v62.html:27906-27907` (финальная живая
  версия функции, используется district perimeter/collector/local,
  arterial master/connector) — позиция бордюра `cmx+nx*side*(s.w*.5+curbW*.5)`
  (внешний край бордюра = `s.w*.5+curbW`), позиция тротуара
  `cmx+nx*side*(s.w*.5+curbW+walkW*.5+.025)` (внутренний край тротуара =
  `s.w*.5+curbW+.025`) — разница ровно `.025`. Тот же паттерн (тот же
  буквальный сдвиг `+.025`) присутствует и в уже неактивных версиях этой
  функции в v57 (`tycoon-v62.html:27483`) — то есть это не опечатка одного
  автора патча, а сознательно повторённый приём.
- Проявление: живой замер на реальном сегменте улицы района `suburb` —
  бордюр `Box3` (`min.z:-39.69, max.z:-39.58`, ширина `0.11` = `curbW`,
  совпадает с константой), тротуар `Box3` (`min.z:-40.055, max.z:-39.715`,
  ширина `0.34` = `walkW` для `s.w>=2.8`) — зазор между внутренним краем
  тротуара (`-39.715`) и внешним краем бордюра (`-39.69`) = `0.025`
  юнита, что при характерном масштабе сцены (рост NPC на скриншотах ≈
  1.7-1.8 юнита) соответствует ~1.5см в пересчёте на «человеческий»
  масштаб — практически незаметно на обычной игровой камере, но реально
  присутствует и однозначно измеримо.
- Первопричина: скорее всего намеренный микро-зазор для избежания
  Z-fighting между двумя копланарными (`y≈0.086` у бордюра, `y≈0.097` у
  тротуара — на самом деле они на разной высоте, так что Z-fighting между
  НИМИ самими маловероятен; более вероятная причина — избежать
  визуального «шва» точного совпадения краёв двух разных материалов при
  использовании `PolygonOffset`/`depthWrite`-трюков в соседних слоях), а
  не забытая арифметика — но с точки зрения буквальной формулировки
  запроса («нет зазоров между элементами покрытия») это всё равно
  измеримый дефект.
- Правильное решение: если зазор не нужен визуально (не видно
  z-fighting), просто убрать `+.025` (тротуар примыкает к бордюру
  вплотную). Если он специально существует для чего-то ещё (не
  подтверждено в этом проходе), задокументировать константу явным именем
  (`CURB_WALK_GAP=.025`) вместо магического числа, повторённого в
  нескольких местах.
- Риск исправления: очень низкий — визуальная косметика, не влияет на
  коллизии/навигацию/трафик.

**[P3] Высота полотна индивидуальных driveway (`addDrivewayMesh`, не тронут v56-v62) не совпадает с константой высоты дорог v59**
- Место: `addDrivewayMesh`, `tycoon-v62.html:13021-13042` (базовый v35 код,
  не входит в цепочку переопределений v56-v62 вообще — подтверждено
  отсутствием этой функции в карте Прохода 2 и повторным грепом в этом
  проходе) — плита `position.y=0.048`, высота `0.03`, верх плиты ≈`0.063`.
  Сравнить с `ROAD59.surfaceTop=.075` (`tycoon-v62.html:27846`,
  используется как опорная высота верхней поверхности дорожной разметки в
  v59/v60/v61) и высотой самого дорожного полотна у `addRoadDeck59`
  (`y=.058`, толщина `.034`, верх ≈`.075`) — то есть верх individual
  driveway на ~0.012 юнита НИЖЕ верха основной дороги, к которой он
  подходит.
- Проявление: только статический анализ чисел констант в этом проходе (не
  подтверждено скриншотом/живым замером стыка конкретного driveway с
  дорогой — это кандидат для более прицельной живой проверки в будущем
  проходе, если решат чинить). Величина (0.012 юнита) на порядок меньше
  уже найденного 0.025-юнитового зазора бордюр/тротуар, то есть при
  текущем масштабе сцены эффект (видимая ступенька на стыке подъездной
  дорожки и улицы) скорее всего суб-визуален, но является ровно тем
  случаем «константа, которая должна быть общей, но задана раздельно в
  нескольких местах», о котором явно просил раздел 4.
- Первопричина: `addDrivewayMesh` — код до-v37/v38 эпохи, никогда не
  ревизировался при введении `ROAD59`-констант в v59, потому что
  формально driveway (последний отрезок от «обочины» до фасада здания) —
  отдельная, более старая подсистема, о существовании которой авторы
  v56-v62 могли не думать при стандартизации высот основной сети.
- Правильное решение: завести общую именованную константу высоты
  поверхности дороги (например, поднять `ROAD59.surfaceTop` в
  действительно глобальную область видимости вместо приватной `ROAD59`
  внутри IIFE v59, что уже частично сделано через
  `window.__TYCOON_ROAD_SPECS_V59__`) и использовать её в
  `addDrivewayMesh` вместо локального `0.048`.
- Риск исправления: очень низкий — чисто визуальная правка одной
  Y-координаты.

### Не проверено / ограничения этого прохода (честно, для следующего прохода)

та же, что уже зафиксирована в Проходе 2 для других разделов: каждый
новый дорожный патч-слой (v57→v58→v59→v61) переписывал «сборочные»
функции с нуля ради своей конкретной новой цели (текстуры/аудит →
геометрическая точность → инженерные допуски по ширине → curved
corners), и при каждой такой переписи терялась часть уже
существовавшей функциональности предыдущей версии (бордюр/тротуар,
охват страховочной сетки, корректность прогресс-гейта), потому что
ни один слой не сверялся с полным списком фич версии, которую он
заменяет — единственная системная рекомендация для плана v63 по разделу
4: прежде чем писать v63-й дорожный слой, свести все 7 версий каждой
переопределённой функции в один явный чеклист фич (bordюр? тротуар?
разметка? прогресс-гейт? страховочная проверка?) и убедиться, что
финальная версия v63 — объединение, а не очередная замена с нуля.

Инструментирование добавлено ЧЕРЕЗ `page.evaluate`/`addInitScript`, БЕЗ единой правки
`tycoon-v62.html` на диске:
- `scene.traverse` — переопределён как **собственное свойство самого объекта `scene`**
  (не прототипа `THREE.Object3D`!), которое оборачивает исходный
  `THREE.Object3D.prototype.traverse` таймингом и подсчётом узлов. Важное техническое
  замечание для воспроизводимости: патчить сам `Object3D.prototype.traverse`
  напрямую **нельзя** — эта функция рекурсивна (`children[i].traverse(callback)`
  внутри своей же реализации), поэтому обёртка на уровне прототипа считает КАЖДЫЙ
  рекурсивный под-вызов как отдельный «вызов traverse», задирая числа на несколько
  порядков (первая попытка в этом проходе дала 70609 «вызовов» / 194889 «узлов» за
  2.5с загрузки — артефакт метода, не реальное число). Патч на уровне конкретного
  инстанса `scene` (не прототипа) даёт корректные числа, т.к. рекурсия внутри вызова
  идёт через немодифицированный прототип.
- `setInterval`/`MutationObserver`/`requestAnimationFrame` — обёрнуты через
  `page.addInitScript` (выполняется до ЛЮБого скрипта страницы) таймером
  `performance.now()` до/после каждого вызова колбэка, с накоплением `calls`/
  `totalMs`/`maxMs` по каждому зарегистрированному интервалу/наблюдателю/RAF-петле
  отдельно (петли различались по 70-символьному отпечатку исходного текста функции).

### Находки

**[P1] Постоянный полный обход сцены (`scene.traverse`) в бесконечном таймере обновления фонарей — стоимость растёт с размером города, не ограничена culling'ом**
- Место: `updateLampLightingV45()`, `tycoon-v62.html:24901-24912` —
  `scene.traverse(o=>{ if(o.userData?.v45LampLens...) ...; if(o.userData?.v45LampHalo...) ...; })`.
  Вызывается из независимой `requestAnimationFrame`-петли `loop()`,
  `tycoon-v62.html:25157`: `R.frameAccum+=dt; if(R.frameAccum>.18){R.frameAccum=0;
  updateLampLightingV45();} requestAnimationFrame(loop);` — то есть раз в
  накопленные 0.18с игрового времени, бессрочно, на весь сеанс.
- Проявление: живой замер (15с окно в loaded state, инструментирован именно вызов
  `scene.traverse`, не рекурсивные под-вызовы — см. метод выше): **9 вызовов за
  15с**, каждый обходит **~11089 узлов** (общее число объектов сцены в loaded
  state), итого **99801 узел** и **19.2мс** суммарного CPU-времени только на эти 9
  вызовов (под swiftshader; на реальном железе мс/вызов, вероятно, ниже, но не
  ноль — порядок величины числа узлов на вызов — платформонезависимая метрика).
  За более длинное окно (~90с, см. таблицу выше) — 49 накопленных вызовов, 543460
  узлов суммарно, т.е. рост линейный и безостановочный. Сравнение boot→loaded:
  на свежей загрузке (3663 объекта) один такой вызов стоил кратно дешевле, чем в
  loaded state (11069 объектов) — **~3× рост стоимости КАЖДОГО вызова** просто
  от роста города, притом что цель обхода — обновить лишь фонари (десятки
  тегированных объектов), а не 11 тысяч.
  Дополнительное методологическое замечание: реальная частота на устройстве будет
  ВЫШЕ измеренной здесь, не ниже — под swiftshader сама rAF-петля `loop()` тикает
  редко (39 раз за 15с ≈ 2.6 раза/с, замерено отдельно через RAF-инструментирование),
  из-за чего `dt` (зажат `Math.min(.05,...)`) накапливается до порога 0.18 медленнее
  реального времени; на настоящем 60fps-устройстве та же петля тикала бы кратно
  чаще, и порог 0.18с игрового времени набирался бы примерно раз в ~180мс реального
  времени (≈5.5 раз/с) — т.е. полный обход сцены происходил бы ЧАЩЕ, чем
  зафиксировано в этом sandbox-замере.
- Первопричина: `scene.traverse` используется как способ найти объекты, помеченные
  `userData.v45LampLens`/`v45LampHalo` (фонарные плафоны/гало, создаются
  контролируемой фабрикой `installLampFactoryV45`/`makeLampV45`), вместо того чтобы
  хранить их в плоском массиве при создании — ровно так, как уже сделано в этом же
  файле для `sourceTrees`, `npcWorkers`, `livingCityRuntime.cars` и т.д. Стоимость
  такого обхода принципиально не ограничивается frustum culling (обходятся ВСЕ
  объекты графа сцены, включая невидимые/за кадром) и растёт линейно с общим
  числом объектов в сцене, а не с числом реально видимых или реально нуждающихся
  в обновлении фонарей.
- Правильное решение (структурная замена, НЕ понижение качества графики): собирать
  ссылки на `v45LampLens`/`v45LampHalo`-объекты в плоский массив в момент создания
  фонаря (единственная точка создания уже известна и контролируется —
  `makeLamp`/`makeLampV45`) и итерировать этот массив напрямую вместо
  `scene.traverse`. Визуальный результат идентичен, частота обновления та же,
  стоимость становится O(число фонарей), а не O(число объектов сцены).
- Риск исправления: низкий — чисто структура данных; единственное, что нужно
  аккуратно сделать — синхронизировать массив при удалении фонарных групп (когда
  дорожные/районные `refresh*`-функции пересоздают геометрию через
  `disposeObject3D`) — добавление в массив уже привязано к единственной фабрике
  создания, но удаление нужно явно прокинуть в `disposeObject3D` или в конкретные
  пути пересборки, иначе массив будет расти «мёртвыми» ссылками на удалённые
  объекты (сами по себе не утечка памяти — GC соберёт меш, если ничего больше на
  него не ссылается, но нужно проверить, не держит ли такой «мёртвый» элемент
  массива меш живым дольше, чем нужно).

**[P1] Процедурные фабрики декора (деревья/камни/фонари/инструменты NPC) создают уникальные Geometry+Material на КАЖДЫЙ инстанс — почти нулевое переиспользование, подтверждено живыми числами**
- Место: `makeConiferTree` (`tycoon-v62.html:2298-2337`) — ствол+3 ветки корректно
  делят один `trunkMat` (хорошо), но 4 меша кроны (`new THREE.ConeGeometry(...)`)
  и 1 меш верхушки (`new THREE.SphereGeometry(...)`) КАЖДЫЙ получает свой
  `new THREE.MeshStandardMaterial({color: <из палитры на 4 цвета>})` — ни geometry,
  ни material не кэшируются, хотя варьируются лишь незначительным случайным
  размером и выбором из маленького фиксированного набора цветов. Тот же паттерн
  подтверждён построчным чтением `makeRock` (`:2396-2406`, `new
  THREE.DodecahedronGeometry`+`new THREE.MeshStandardMaterial` на каждый вызов),
  `makeLamp` (`:2408-2424`, `new THREE.CylinderGeometry`/`new
  THREE.SphereGeometry`+`new THREE.MeshStandardMaterial` на каждый вызов),
  NPC-инструмента `addWorkerTool` (`:6166-6191`, `new THREE.BoxGeometry`+
  `createWoodMaterial`/`createMetalMaterial` на каждый инструмент), пропов
  стройплощадки (`~:5331`). При этом ТЕКСТУРЫ, на которые эти материалы
  ссылаются, кэшируются корректно (`materialTextureCache`/`getWoodTexture`/
  `getGlassTexture`/`getSmokeTexture` — Map-кэш по ключу) — это asymmetричная
  находка: кэширование текстур в файле УЖЕ есть и работает, но материалы-обёртки
  вокруг них и геометрии — нет.
- Проявление: живой замер loaded state — **9838 мешей** против **9587
  уникальных `geometry.uuid`** (переиспользуется лишь 2.5% геометрий) и **5101
  уникальных `material.uuid`**. Для сравнения — `renderer.info.memory.textures`
  стабильно **22-23** весь тест (текстуры реально переиспользуются). 65 живых
  `sourceTrees` в loaded state → это одна из крупнейших статей вклада в те ~9838
  мешей (каждое дерево — ствол+3 ветки+4 кроны+верхушка+опционально куст =
  8-9 мешей, из которых 5 несут уникальную geometry+material).
- Важная оговорка (отделяем реальную проблему от преждевременной оптимизации,
  как явно просил пользователь): это **НЕ** проблема draw calls/пропускной
  способности рендера сейчас — `render.calls` в loaded state всего 359 (frustum
  culling исправно работает, большинство из 9838 мешей не рисуется в конкретном
  кадре), и это не то, что стоит "чинить ради FPS". Реальная, измеримая стоимость
  — (а) объём JS heap (9587+5101 отдельных JS/WebGL-объектов вместо ограниченного
  пула из ~20-30 переиспользуемых комбинаций geometry/material под визуальные
  архетипы) и (б) отложенная GPU-память: `renderer.info.memory.geometries` в этом
  тесте всего 2007-2073 (в ~4.6 раза меньше 9587), потому что Three.js
  загружает geometry в GPU только при первой реальной отрисовке — по мере того,
  как игрок реально обойдёт отстроенный город камерой, это число будет расти к
  фактическим ~9587 (каждая уникальная geometry — отдельный GPU-буфер), тогда как
  при переиспользовании общий тираж GPU-буферов остался бы на уровне десятков,
  независимо от того, сколько деревьев/камней/фонарей реально настроено.
- Первопричина: ни одна из этих фабрик не была написана с идеей «один и тот же
  визуальный вариант → одна и та же instance geometry/material»; каждый вызов
  делает `new`.
- Правильное решение (структурный кэш, НЕ понижение графики — переиспользует уже
  работающий в файле паттерн кэширования текстур): кэшировать geometry/material по
  «рецепту» (вид дерева+размерный бакет+индекс цвета для деревьев; размерный
  бакет для камней; один набор геометрий для фонарей; вид инструмента для NPC) в
  `Map`, по образцу уже существующего и рабочего `materialTextureCache`.
  Визуальный результат идентичен, поскольку варьируемые входы и так берутся из
  маленьких фиксированных дискретных наборов (4 цвета листвы, 2-3 размерных
  бакета, 2 вида дерева) — это чисто кэш/переиспользование, не даунгрейд.
- Риск исправления: средний — часть этих мешей анимируется по отдельности (яркость
  `emissiveIntensity` у фонарного плафона в `updateLampLightingV45`, тонировка
  стёкол и т.п.) — общий (shared) material-инстанс для таких случаев нужно либо
  не шарить (оставить фонарный плафон индивидуальным — он и так дешёвый, фонарей
  немного), либо перенести анимируемое свойство на уровень геометрии/атрибута, а
  не material; для статичных элементов (деревья, камни) риск минимален. Нужен
  аккуратный проход по каждому типу объекта, а не один слепой блокирующий фикс.

- Риск исправления: низкий-средний — нужно убедиться, что перенос

- Правильное решение: `v44InstallObserver()` (`:24559-24561`) уже вешает

  пути; либо убрать/сильно проредить периодический вызов, либо сузить область
  `querySelectorAll` вместо `document` целиком.
- Риск исправления: низкий — нужно только проверить кейс, где у уже

  но реальное влияние ничтожно при жёстко ограниченной живой популяции в 4
  объекта — не выделено отдельной находкой, покрыто общей Находкой №2 выше.
- **Память/утечки за ~90с в loaded state** (не только early game, как в Проходе 2)
  — `render.calls`/`triangles`/`memory.geometries`/`memory.textures` абсолютно
  плоские, JS heap без монотонного роста (60-63МБ) — расширяет вывод Прохода 2 на
  полностью отстроенный город.
- **DOM reflow** (`offsetWidth`/`getBoundingClientRect` рядом с записью стиля) —
  грепом найдены все вхождения; все относятся к намеренному паттерну «перезапуск
  CSS-анимации» (`classList.remove(...); void el.offsetWidth; classList.add(...)`),
  каждое гейтовано условием изменения состояния (например,
  `V47.lastGoal!==title`) или событием пользовательского ввода
  (`pointerdown`), ни одно не вызывается безусловно в hot per-frame/per-interval
  цикле — это НЕ classic forced-synchronous-layout антипаттерн, который искал
  раздел 3, находки нет.

Раздел 3 из 18-пунктного ТЗ закрыт. Найдено 2 P1 (постоянный полный `scene.traverse`

### Находки

**[P1] Жители массово «упираются в стену» навсегда: цель выбирается случайной точкой внутри коллайдера здания**
- Место: `chooseResidentTarget`, `tycoon-v62.html:11081-11099` (случайный радиус 11097-11098:
  `rad = …1.65+Math.random()*.8` вокруг якоря-участка); движение `updateLivingCity`
  11142-11176 (стоп-условие только `dist<.18`, 11149; `resolveAgentPosition(…,.18,obstacles)`
  11172); коллайдеры участков `cityWorldRuntime.plotColliders` (радиус 1.75) в
  `agentObstacleCircles` 11960.
- Проявление: к концу 90-150-секундных трасс **10 из 14** (run1 B) и **12 из 14**
  (run2 B) видимых жителей числятся «идущими» (цель дальше 0.18), но за последние 20 с
  сместились меньше чем на 0.3; у 9 и 12 из них соответственно цель лежит **внутри**
  круга препятствия. Типичный житель стоит, прижатый ровно к границе круга (запас
  −0.003 юнита до `r+0.18`), и «шагает на месте» (анимация ног идёт по фазе, 11175).
  В короткой фазе A таких 0-1 — проблема накапливается: каждая новая цель с шансом
  ~половина попадает внутрь участка, и выхода из этого состояния нет.
- Первопричина: цель — не точка доступа (дверь/тротуар перед участком), а случайная точка
  в кольце 1.65-2.45 вокруг центра участка, тогда как сам участок — препятствие радиусом
  1.75. Проверки «цель достижима» нет, счётчика «не приближаюсь к цели» нет, у жителей нет
  даже того спасателя, что есть у рабочих.
- Правильное решение: у каждого здания/участка — явная точка входа (например, точка на

- Риск исправления: низкий-средний — точки входа нужно согласовать с тротуарами v59
  (иначе жители будут стоять на проезжей части и блокировать машины, см. следующую

- Риск исправления: высокий — меняет всю геометрию улиц и проверенные Проходом 3 допуски;

(1) жители — 86 % застревают навсегда у стен, потому что цель — случайная точка внутри

длины кузова; (3) игрок, просто стоящий на точке спавна, намертво останавливает всю

района проложены прямо через здания этапов 4 и 7; (5) у рабочих нет фазы ресурса, работа —
1.2 % времени, 68 % — переходы через весь город.

Общая причина большинства находок та же, что в Проходах 2-4, но здесь она видна особенно
ясно: **в игре пять независимых движков ТС** (`moveWorkVehicle`, `moveLivingCar`/
`moveDistrictLocalCar`, `moveArterialCar`, `moveWaypointCityVehicle`, `updateTransitV40`) и
**две независимые системы пешеходов** (рабочие, жители), у каждой — своя шкала скорости,
свой способ уступать, своя модель поворота и свои «спасатели». План v63 по разделам 5-6
должен начинаться не с очередного фикса поверх, а с одной общей модели движения
(дорожный граф с полосами → следование за машиной впереди → ограничение поворота по
радиусу → заданные точки подъезда/выгрузки/работы у каждого здания) и одного
пешеходного графа по тротуарам для рабочих и жителей; после этого большая часть
находок (прохождение сквозь машины, развороты на месте, задний ход на углах, вечные
тупики с жителями, работа в стенах) закрывается одним изменением, а спасатели v60/v62
удаляются.
